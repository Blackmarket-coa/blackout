# Blackout Threat Model

This document is the authoritative top-level threat model for Blackout. It defines the adversary classes we defend against, the trust boundaries in the system, the assets we protect, and the residual risks we have explicitly accepted. Narrow per-feature threat models live alongside their features and are linked from §6.

## 1. System sketch

Blackout is a federated, end-to-end-encrypted communication platform built on the Matrix protocol with a LiveKit-based real-time media plane. The clients are a web app, a Tauri desktop app, and a React Native mobile app. The server side is a Synapse-derived homeserver, a Node API, a LiveKit SFU, and ancillary services (media repo, push gateway, OIDC).

```
┌──────────────────┐      E2EE (Megolm/Olm)        ┌───────────────────┐
│ Client (web /    │◀──────────────────────────────▶│ Other client      │
│ desktop / mobile)│   ciphertext relayed via       │ (any homeserver)  │
└────────┬─────────┘   Matrix federation            └───────────────────┘
         │
         │ TLS / Matrix CS API
         ▼
┌──────────────────┐    federation (HTTPS+sigs)    ┌───────────────────┐
│ Blackout         │◀──────────────────────────────▶│ Other homeservers │
│ homeserver       │                                └───────────────────┘
└────────┬─────────┘
         │ signaling (encrypted to_device events)
         ▼
┌──────────────────┐    DTLS-SRTP (+ SFrame E2EE)
│ LiveKit SFU      │◀──────────────────────────────▶ Clients (calls)
└──────────────────┘
```

## 3. Trust boundaries

1. **Client ↔ homeserver.** TLS-protected. Homeserver is _trusted for routing/availability_, _untrusted for content_ (Megolm/Olm protect plaintext).
2. **Homeserver ↔ federated homeserver.** Server-signed events, perspective key servers. Each homeserver is trusted only for its own users.
3. **Client ↔ LiveKit SFU.** DTLS-SRTP today; SFU sees plaintext frames. After improvement A1: SFrame E2EE removes SFU from the trust boundary for media confidentiality.
4. **Client ↔ OIDC IdP.** IdP is trusted for identity assertion. Token lifetimes, as configured here: the Blackout API's access token lasts 24 hours and its refresh token 30 days, renewed with each use; a Matrix access token lasts 5 minutes and its refresh token does not expire unless the operator sets `refresh_token_lifetime`, which none of the homeserver templates here does; the IdP's own lifetimes are its configuration. Until 2026-11-16 this said "tokens are short-lived".
5. **Build pipeline ↔ release artifact.** `release.yml` signs the container image and the release files with cosign (keyless, Sigstore) when a `v*` tag is pushed. No tag has been pushed and no release exists, so nothing has been signed; builds are not reproducible; the desktop updater's public key in `blackout-desktop/src-tauri/tauri.conf.json` is a placeholder. Until a signed release exists, a client is whatever was downloaded.
6. **Per-device boundary.** Each device has its own Megolm/Olm keys; cross-signing binds them under one user identity. Verification would extend the boundary to a peer device, but the app offers none: its emoji (SAS) dialog is on a settings page nothing renders, and QR is not enabled (`verificationMethods: ['m.sas.v1']` in `client/initMatrix.ts`). Another Matrix client can verify the devices.
7. **Client ↔ call.element.io (optional).** A voice channel or a stage can open Element Call, a page Element runs, loaded only when the person asks (`CallWidget.tsx`). Loading it sends Element the person's network address and the room's ID; what Element's service does with a call is outside this repository. Until 2026-11-16 it loaded on joining, with nothing said.
8. **Client ↔ the deployment's tile server.** The coalition map draws its background (streets, water, place names) from the deployment's own Martin, at `/tiles/` beside `/v1/`: the basemap from a Protomaps extract the operator downloads once (`infra/single-server-baseline/martin/fetch-basemap.sh`), the label fonts from files checked in beside `martin.yaml` (`coalition/tabs/basemapStyle.ts`). That server sees the area on screen, as it sees the rest of the person's traffic, and so does anything in front of it that ends TLS: the live host is served through Cloudflare (`docs/deployment/production.md`), which sees each tile's address, and so the area on screen, with the person's network address. The map asks no other service for anything; without a basemap the pins are drawn on a plain background, and the map says the background did not load. An operator who sets `VITE_MAPLIBRE_STYLE_URL` replaces all of this with their own style, and whoever serves that style and its tiles sees the area on screen. Until 2026-11-17 the map loaded `tile.openstreetmap.org` whenever no style was set, which no deployment file here did, sending OpenStreetMap the person's network address and the area on screen.
9. **Client ↔ Google reCAPTCHA (optional).** If the homeserver asks for a CAPTCHA at registration, the sign-up page loads Google's script (`RegisterForm.tsx`). None of the homeserver templates here turns it on.
10. **Client ↔ Free Black Market and GIF providers.** A public creator page (`/@handle`) fetches the store from `api.freeblackmarket.com` and shows its images from wherever they are hosted. When the API holds a Giphy or Tenor key (none by default), the GIF picker shows thumbnails from the provider's servers; the GIF chosen is fetched through the API.

## 4. Assets

-   Message plaintext (DMs, channels, threads, replies).
-   Scheduled message text (held by the API as plaintext until the bot sends it).
-   Call and townhall media plaintext.
-   Attachment plaintext, and for files sent before 2026-11-16 the files themselves, which the media repository holds unencrypted.
-   Deaddrop payload plaintext (no shipped flow creates one; see §5).
-   Dead-man switch records (owner, room, recipients, timing, label, payload as the owner sent it).
-   Public geocache records (behind `BLACKOUT_COALITION_CACHES`, off): the exact spot each placer chose, which only the placer and administrators are sent; others see a 50 m area, from 2 to 3 hours after placing (random per cache), with no placer or times. Exclusion zones, which may mark shelters and clinics, are never revealed to members. Consent records, including the person's own 18+ statement. Adversary A14 applies; `docs/security/coalition-caches-2026-11-22.md`.
-   Release identities: the public halves each person publishes to the API, the private halves on their devices and in their recovery files, and each device's record of whom its owner compared safety codes with.
-   Cross-signing master / self-signing / user-signing keys.
-   Per-device Megolm/Olm keys and key backup.
-   OIDC refresh tokens.
-   Governance vote ballots and tally inputs.
-   Federation peer keys and trust state.
-   Audit logs (ordinary database rows; see §5).
-   User social graph and metadata (room membership, presence, who-talks-to-whom, timing).
-   Coalition platform credentials (shared and member connection secrets).
-   Inbound external replies (third-party text held for moderation).
-   Campaign attribution and engagement counters.
-   FBM manage-billing links (short-lived bearer capabilities over a member's FBM subscriptions).

### 6a. Third-party plugin code (marketplace installs)

**Asset**: code-bearing plugins purchased through a connected marketplace
(`code_plugin` artifact kind under `packages/api/src/routes/creator.ts`,
loaded by `apps/blackout-client/src/app/features/monetization/install/pluginInstaller.ts`).

**Threats**:

-   **Spoofing/Tampering**: a man-in-the-middle or compromised CDN serves a
    malicious bundle. Mitigated by requiring an Ed25519/HMAC signature
    envelope (`PluginSignatureEnvelope` in
    `packages/blackout-protocol/src/plugins/index.ts`) covering both the
    canonical manifest hash and the bundle SHA-256. The blackout client
    refuses to install if the key id is not on its pinned keyset
    (`apps/blackout-client/src/app/features/monetization/install/pluginSignature.ts`).
    A production build trusts only Ed25519 keys pinned when it is built
    (`publishingKeys.ts` beside it, or `VITE_PLUGIN_PUBLISHING_KEYS` for one
    build) and refuses every HMAC key; the HMAC key the API's stub
    marketplace signs with (`fbm-dev-hmac`) is in development builds only.
    **No key is pinned yet:** until the operator pins Free Black Market's
    public key (`tools/plugins/publishing-key.mjs`), a production build
    installs nothing bought from the marketplace, plugin or otherwise. Until 2026-11-17 that development key was the only
    one, in every build, so anyone with the client could sign a bundle it
    would install (trust-claims T22).
-   **Privilege escalation inside the host**: plugin code attempts to read
    cookies, call host APIs, or open Matrix sessions. Mitigated by hosting
    bundles in a `sandbox="allow-scripts"` `srcdoc` iframe with no host
    DOM or storage access; all interaction goes through a typed postMessage
    RPC bridge gated by capabilities declared in the manifest
    (`PluginCapability`, enforced in
    `apps/blackout-client/src/app/features/monetization/install/sandbox/PluginSandboxHost.ts`).
-   **Lateral movement to other plugins / users**: each sandbox instance is
    scoped to a single plugin id and does not share state with other
    plugins. Capability denials are logged and surfaced in
    Settings → Plugins so the user can revoke.
-   **Repudiation / persistence after revocation**: when an entitlement is
    revoked or a `creator.account.suspended` lifecycle event arrives, the
    installer unregisters the dynamic plugin and the sandbox iframe is
    destroyed. The signed bundle is not retained outside the active
    install record.
-   **Embedded checkout iframe abuse**: the marketplace embed iframe runs
    with `sandbox="allow-scripts allow-forms allow-same-origin
allow-top-navigation-by-user-activation"`; the host only relays
    `checkout.completed` / `checkout.cancelled` postMessage events whose
    origin matches the redirect URL, and refuses any other origin or
    payload shape.

**Residual risk**: a plugin that is granted broad capabilities (e.g.
`message.compose`) can still misbehave within those capabilities. The
manifest is shown to the user before install and capabilities can be
revoked from Settings → Plugins. Whoever holds the private publishing key
can sign bundles every build pinning it will install. Free Black Market runs
on the same server as the API, so whoever takes that server can sign them,
as they could already change the web client it serves; a desktop or mobile
build keeps trusting a pinned key until a new build drops it.

### 6b. FBM-hosted subscription management (manage session)

**Asset**: a link to Free Black Market's hosted subscription management page
(Settings -> Subscriptions -> "Manage billing on Free Black Market"). The
token in its path lets whoever holds it turn off automatic renewal or cancel
the member's FBM subscriptions until it expires. Contract:
`docs/contracts/fbm-billing-consumer.md` (§"Subscription management").

FBM-side properties are **contract requirements, not verified behaviour**:
the manage-session contract requires FBM to expire the token after 15
minutes, revoke earlier tokens on a new mint, store only the token's sha256,
and serve the page with `frame-ancestors 'none'`. FBM is building the endpoint
and page in parallel; none of this has been checked against a live FBM yet.
Blackout's own mitigations below do not depend on them.

**What FBM learns**: the Blackout user id (sent as `blackout_user_id`) and,
from the member's purchases, their billing identity. The card processor FBM
uses sees the card. None of this is private from FBM, and the screen does not
say it is. FBM receives no message content, keys or room data from this flow:
the only other thing sent is an optional return link, which the client builds
from the app origin alone and the API cuts down to origin plus `/` whatever it
is sent, so the open space, room or event id never reaches FBM.

**Threats and mitigations**:

-   **Minting a link for someone else**: the user id comes only from the
    verified Blackout token (`user.sub`); a body `userId` is stripped. FBM
    answers `409 identity_ambiguous` rather than picking one when more than one
    FBM customer carries the id, and Blackout passes that through as a refusal.
-   **Link leakage**: the API returns the link and nothing else touches it — no
    log line, no audit detail (the audit row has the expiry only), and
    `cache-control: no-store`. The client opens it with `noopener,noreferrer`
    or the system browser, so no `Referer` or opener handle carries it.
    Residual: the link is in the browser history of the tab FBM opens in, and
    on the web the screen keeps a fallback anchor to it until the page is left.
    The short expiry bounds both.
-   **Open redirect / phishing through a tampered API response**: the client
    opens the link only when its origin is on the build-time pin
    (`VITE_FBM_MANAGE_ORIGINS`, default `https://api.freeblackmarket.com`) and
    its path is FBM's manage page with no query or fragment; anything else is
    refused. The provider applies the same check first: it returns a link only
    when it is on the `FREEBLACKMARKET_BASE_URL` origin and is exactly FBM's
    manage-page path, with no credentials, query or fragment.
-   **Clickjacking / framing**: Blackout never puts the page in an iframe; it
    opens it through the external-purchase opener (the Capacitor system
    browser on Android and iOS, the system browser through
    `tauri-plugin-opener` on the desktop shell — https only, by capability
    scope — and `window.open` with `noopener,noreferrer` elsewhere). Per the
    contract FBM must also serve it with `frame-ancestors 'none'` (not yet
    verified). The desktop path is compile-checked but not yet exercised in a
    running desktop build, and falls back to `window.open` if the plugin
    refuses; the copy therefore still says only that the page is hosted by
    FBM, not that it opens outside Blackout.
-   **Open return link**: a `returnUrl` is forwarded only when its origin is
    in an explicit `CORS_ALLOWED_ORIGINS` list (a `*` wildcard, which is
    refused in production anyway, forwards none) or it is the native
    `blackout://checkout/return` link, and FBM applies its own allowlist on
    top. A forwarded web link is reduced to its origin plus `/`.
-   **Availability**: fail-closed. The server switch
    `FBM_MANAGE_SESSION_ENABLED` defaults off (503), FBM's own flag answers
    `404 feature_disabled` (mapped to 503; any other 404 is a misconfiguration
    and answers 502), and the client section is behind `accountSubscriptions`
    (default off, except that a beta build with `VITE_BLACKOUT_BETA_UNLOCK_ALL`
    turns every client flag on, this one included; the server switch still
    answers 503 there). Where purchase links are blocked (iOS outside the US)
    the button is hidden.

**Residual risk**: changes made on FBM reach Blackout by webhook, so the
Blackout screen can lag; the UI says so instead of claiming changes are
immediate.

### 6c. Black Mask chat panel (embed route and framing)

**Asset**: a signed-in Blackout session rendered at `/embed` inside a frame on
another origin (the Black Mask extension). Spec and status:
`docs/black-mask-chat-panel-and-account-link.md` (steps 1 to 3).

**Who can frame it**: nobody by default. The web client's nginx image sends
`frame-ancestors 'none'` and `X-Frame-Options: DENY` on every route. On `/embed`
and `/embed/*` only, it sends `frame-ancestors <list>` when
`BLACK_MASK_FRAME_ANCESTORS` holds a valid list of origins. Listing an origin
**trusts that origin not to clickjack the panel**: the framing page controls
the frame's size, position and what is drawn over it. It cannot read the
panel's content (same-origin policy) and the panel sends it nothing (no
`postMessage`, no unread counts).

Behind the `infra/nginx` or single-server-baseline proxy (2026-10-11), the
proxy adds `X-Frame-Options: DENY` and `frame-ancestors 'none'` to every
HTTPS response for `theblackout.app` and `chat.theblackout.app`, except on those two
panel locations when the container's complete response header block carries a
`frame-ancestors` list in the form the image writes; there it leaves its own two
out and repeats the container's list. So behind a proxy the container's list
is still the only way to allow framing, and the proxy trusts the container to
send the right list on `/embed`.

**Threats and mitigations**:

-   **Clickjacking by an unlisted site**: refused by the browser. Checked in a
    real Chromium: an unlisted origin is refused both `/embed` and `/`.
-   **A mistyped or over-broad allow-list**: each entry must be a bare origin
    (no wildcard, path, keyword or CSP syntax), and one bad entry rejects the
    whole list, so the panel stays `'none'`
    (`apps/blackout-client/nginx/docker-entrypoint.d/40-black-mask-frame-ancestors.sh`).
-   **The full app served under the panel's policy**: the client decides
    "panel or full app" once, from the path it loaded on (`main.tsx`), and
    nginx refuses panel requests whose raw URI does not literally start with
    `/embed` (encoded or doubled-slash variants it would otherwise normalise
    into the panel's locations).
-   **A front proxy relaxing more than the panel**: the proxies apply the same
    raw-URI test and relax only when the container sends a `frame-ancestors`
    list (not `'self'`, a wildcard or another directive) in a header block
    nginx read completely. When the container is down, too slow or sends a
    broken header block, nginx's own 502 or 504 keeps the usual headers, and a
    client image from before the panel leaves everything unframeable. Not
    covered: after a complete header block with the list, nginx's own 404 or
    500 for an `X-Accel-Redirect` goes out under that list; the client image
    sends none. `tools/ci/check-embed-proxy-framing.mjs` compares the panel
    maps and locations with a pinned form and fails if the panel's variables
    are written or used anywhere else in the proxies' files; it does not run
    nginx and cannot see files a host adds. Checked against real nginx and
    Chromium, not on a deployed host.
-   **The panel's frame navigating into the app**: every link click inside the
    panel is intercepted. Panel content stays in the panel, everything else
    opens a new top-level tab with `noopener,noreferrer`, and code-driven
    navigation is parked on an in-panel card. SSO, which would redirect the
    whole frame, is not offered in the panel.
-   **Phishing through links in messages**: **not mitigated by the panel.**
    Black Mask's link check (launch-plan B6) is not built; an external link
    opened from the panel is as safe as the same link opened from Blackout.
-   **A panel session left behind, or its tokens copied** (A7: a shared or
    borrowed device, a token lifted from browser storage): the person picks a
    session length at sign-in (step 3). Off by default, behind three switches:
    the web client's build-time `VITE_BLACKOUT_PANEL_SESSION_LENGTHS` (without
    it the panel offers no choice), `session_lengths_enabled` in the homeserver
    module and `BLACKOUT_SESSION_LENGTHS` on the API. With all three on, the
    servers end the panel device's Matrix tokens, and the API tokens exchanged
    for them, at that time without relying on the client. The homeserver caps the device's access and refresh tokens at the
    end and then deletes the device (tokens, E2EE device keys, pushers); the
    API caps the JWT (`exp` and `sxp`) and the refresh-token family at the
    same end, takes the end from the homeserver, never from the client, and
    refuses timed sessions when it has nowhere to keep the end. The length can
    be set once per device and never extended. A timed length is never offered
    unless both servers say they enforce it. Not covered (step 3, "Not
    enforced"): a Matrix OpenID token minted before the end stays valid for up
    to an hour after it, device or not, and lk-jwt-service trades it for
    LiveKit tokens; until the sweep deletes the device, an ended token is still
    accepted by Synapse's `/logout` and `/logout/all` (the latter signs out
    every device of the account); an API refresh token that a modified
    client kept still refreshes after the panel's Sign out, up to the session
    end (for "Until I sign out", for as long as it is refreshed at least once
    every 30 days); and API tokens that a modified client gets by exchanging
    its Matrix token before the length is set are not tied to the session's
    end.
-   **The panel picking up, or clobbering, the full app's session**: with the
    client switch on, the panel keeps its session, API token and IndexedDB
    stores under its own names, so it never runs on the full app's session
    (which has no length), never overwrites it and never prunes its encryption
    keys, partitioned storage or not. With the switch off (the default) it uses
    the full app's names, as before B3.

**Residual risk**: what a panel session did while it was valid is not undone
when it ends (messages, joins, integration secrets created through the API, a
voice token of up to two minutes, and a call joined with it, which LiveKit's
server keeps up with ten-minute tokens of its own, an OpenID token of up to an
hour); the panel
deletes its local stores only when it next runs, so a browser that never opens
it again keeps them on disk; a device whose length could not be bound, and
whose sign-out then also failed, stays in the device list with tokens nothing
holds; under MAS the feature is unavailable. The homeserver's enforcement is
tested only by hand: CI runs no `apps/blackout-server` tests. With the client
switch off, whether a framed panel shares the browser's Blackout session
depends on the browser's storage partitioning for extension-embedded frames,
and has not been checked. Firefox extension origins are per-install, so a
fixed list cannot name the Firefox extension. Anything in front of the proxies
(the live host sits behind Cloudflare) has not been checked for what it does
with these headers. All are recorded as constraints, not solved.

## 8. Release-blocking criteria (summary)

A release is blocked unless:

1. No open Critical/High vulnerabilities in application code, deps, or container images.
2. Authorization test suite passes 100% for new/changed endpoints.
3. Governance integrity tests pass (anti-replay, anti-double-cast, deterministic tally).
4. Federation trust controls validated (peer auth, sig verification, key rotation).
5. Security telemetry verified in staging.
6. This document updated for any feature that crosses a trust boundary or adds a new asset.
7. Security sign-off recorded and linked to the release artifact.
8. Inbound external sync (`BLACKOUT_COALITION_EXTERNAL_SYNC_ENABLED`) is not enabled on a deployment where the external-reply retention sweep is disabled (`BLACKOUT_COALITION_EXTERNAL_RETENTION_SWEEP=0`).

(Full criteria in `docs/security/epic_security_review.md` §5.)
