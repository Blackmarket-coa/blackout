Trust

What Blackout promises, and how to check each promise yourself without taking our word for it.

Every claim below links to the code that makes it true. If a link ever stops supporting the claim next to it, the claim is wrong and we want to know — see SECURITY.md.

Last reviewed: 2026-08-10; section 1 updated 2026-10-18 with the defaults for new canopies and dens; section 2 updated 2026-10-26 with release keys in the export. Changes to anything here are recorded in the policy changelog.

1. Encryption, never behind a paywall

End-to-end encryption is free, on every tier, and there is no mechanism by which it could be sold.

That last part is the one worth checking. Paid features in Blackout are gated by features.* entitlement keys, and the complete catalogue of them is the seven tier tables unioned in entitlements/bundles.ts. None of them contains an encryption key. Not "encryption is set to free" — there is no switch. Turning encryption into a paid feature would require adding one, in a diff, in public.

Every private room and direct message is end-to-end encrypted by default.

  • The API cannot create a room without deciding: createRoom takes a required encrypted flag (matrix-client.ts), so the compiler rejects a new call site that stays silent.
  • The clients set encryption at room creation, not afterwards (matrix-crypto.ts).
  • The homeserver backstops it with encryption_enabled_by_default_for_room_type: invite.
  • CI fails the build if any of that regresses: check-room-encryption.mjs.

What a new room is before you choose. The access chooser sits at the top of the New canopy and New den forms, and what it starts on depends on where you are:

  • In the Blackout app, a new canopy or den is public and not end-to-end encrypted unless you choose otherwise. A den created inside a canopy that is not public starts restricted to that canopy's members and encrypted.
  • In the Black Mask chat panel (/embed), a new canopy starts private (invite-only) wherever you make it, and a new den starts private or, inside a canopy, restricted to that canopy's members; a den is encrypted. The panel's New canopy and New den screens use these defaults. The panel has no invite screen: you invite people from Blackout.
  • An operator can make the app start private everywhere by building the client with VITE_BLACKOUT_NEW_ROOM_DEFAULT=private (newRoomDefaults.ts holds the whole table).

A public canopy is listed in the Blackout canopy directory; any other canopy is listed only if you turn "List in the Blackout directory" on when creating it. These are the client's defaults, not a server rule: the homeserver accepts whatever access a client asks for, and the directory accepts a listing from any of the canopy's admins, whatever its join rule. Encryption is decided when a room is created; changing who can join later does not add or remove it.

This was not true before 2026-08-10. Thirteen server paths and five client paths created plaintext rooms, and the homeserver was not compensating. We found it by auditing our own claim before publishing it, and the full write-up — including what was broken and for how long — is public: 2026-08-10 encryption audit.

The Blackout bot reads no messages, and no bot this repository runs by default can decrypt them. The API's bot creates rooms, invites, moderates membership, reads room state and posts. It has no code that fetches message events: every call it makes to the homeserver's client API is in matrix-client.ts. It has no encryption keys, so it could not read an encrypted message if it tried. Its token is a homeserver admin token: this is a fact about the code, not a limit on the token. The moderation bot (Draupnir), which the Docker deployment runs, reads the messages of the unencrypted rooms it protects; it cannot decrypt encrypted ones unless the operator turns on the Pantalaimon proxy for it (DRAUPNIR_PANTALAIMON_USE, off by default). A bridge or bot an operator adds, or one a room's members invite, can read what is sent in the rooms it is in, encrypted rooms included when it is set up for encryption. A room's member list shows who is in it.

Nothing logs your messages. No log line, error report, or analytics event carries message content. There is no PostHog, no Segment, no session replay in the product. The redactor treats content-shaped fields as secrets (patterns.ts) so this holds even if someone later adds a well-meaning debug line.

What is not encrypted, named plainly

Encryption claims are only worth something with the exceptions attached.

  • Files sent from a build of the app older than 2026-11-16. Until then the app uploaded every attachment, voice note and hidden-message image as it was, in encrypted rooms too. The message around the file was encrypted; the file, its name and its type were not. Those files are still on the homeserver, readable by whoever runs it or holds its backups and by anyone who has a file's address, and the app cannot delete them: deleting the message does not remove the file. Since the fix, a file sent in an encrypted room is encrypted on your device before it is uploaded, and every file that was not is marked in the conversation: "Not end-to-end encrypted". A copy of the app built before the fix keeps uploading unencrypted until it is updated. The full account, including what was not fixed, is in attachment-encryption-2026-11-16.md.
  • What the homeserver sees in an encrypted room. Not the text of messages or the contents of files. It does see who is in the room, who sends something and when, and which earlier message a reply, an edit or a reaction points to; emoji reactions, which Matrix does not encrypt; for a file, its size to the byte, who uploaded it, and the network addresses it is downloaded from; and everything kept as part of the room itself, because Matrix does not encrypt room state in any room: its name, topic and picture, its pinned messages list, role assignments, and the text of den documents, proposals, objectives and playbooks.
  • Publicly joinable rooms. Encrypting a room anyone can join hides history from everyone who joins later and breaks search, without making public content private.
  • Service rooms the Blackout bot posts into — marketplace vendor, order, inventory and ledger rooms, #bugs, and the standing public rooms. The bot is a plain HTTP client with no Megolm implementation, so it cannot encrypt: anything it posts is plaintext, even in an encrypted room. In the encrypted rooms it creates, it posts only room state — den classification, room type and dispute status, which Matrix never encrypts — and, in dead-drop delivery rooms, a delivery notice. Encrypting the service rooms would not make them private, it would break them. Giving the bot real crypto is on the roadmap; until it lands, this list stands and stays here.
  • Scheduled messages. When you schedule a message, you hand its text to the Blackout API. The API stores it as plaintext until it is sent, then clears it, and the bot posts it unencrypted under your name. The API refuses to schedule into an encrypted room, into a room you are not in or may not post in, and into a room the bot is not in, and it checks again right before sending.
  • The API message endpoint (POST /v1/messages/…, used by the Expo mobile scaffold in packages/mobile) stores the text readable on the server whatever stegoTier a client asks for, and says so: every row reads isEncrypted: false, and a request to sign a message is refused rather than answered with something that is not a signature. Until 2026-10-25 tier 2 was labelled e2e; it was an XOR against a server-minted string, recorded in api-findings-triage-2026-10-25.md. If you name a room, the bot posts the text there unencrypted after the same room check.
  • Spaces, which hold hierarchy state and never messages.
  • Calls and townhall media. The app cannot start a call itself today, so it encrypts none: its call path (CallProvider.tsx) asks the Matrix library for a call session that the version the app is built with does not have, and the in-call indicator says "No media E2EE". Until 2026-11-16 this page said per-call media encryption was "negotiated by default". A voice channel or a stage can open Element Call instead, a page from call.element.io that Element runs; the app says so and loads it only when you ask. Loading it sends Element your network address and the room's ID, and what Element's service does with the call is up to Element. Background in THREAT_MODEL.md §3 and R2.

The distinction we will not blur

"E2EE is never paywalled" is true. "Privacy is never paywalled" is not, and we do not say it.

Privacy-enhancing features beyond encryption are tiered: image perturbation, persona compartments and rotation, mesh transport, active defense. The confidentiality of your messages is free; some of the tools for hiding that you are communicating at all are not.

Dead drops are not among them yet, because nobody can use one. The sealed-envelope format, the service that would hold envelopes and the tier limits for them (64 KB, 24 hours, one recipient and no decoys on the free tier) are in the repository and tested, but no screen of the app sends or opens a dead drop, and no deployment file here runs that service. Until 2026-11-16 a room could be put in a "Dead Drop" mode whose banner said your message "will be queued" and whose settings offered "anonymized delivery" on a paid tier. Neither existed: the message was sent at once, under your own name. The mode now says so (trust-claims-2026-11-16.md, T8).

Tor transport and decoy traffic are not built. Paid tiers are assigned them, and until 2026-11-16 this page listed them with the features above. There is no Tor or onion-routing code and no cover-traffic generator in the app. Blackout does not route your traffic through Tor and sends no decoy traffic, on any tier, so the server you use sees the IP address you connect from. The app labels both "planned", a marketplace listing that includes either says "planned, not built yet", and the code that records which hardening features exist is entitlements.ts.

Open, not hidden

Some users see "unable to decrypt" on older messages when they sign in on a new device. Blackout doesn't yet have a screen that restores message keys from a key backup or receives them from your other sessions, so this happens even when a backup exists. A backup still lets another Matrix app with your recovery key restore the messages whose keys are in it, provided the backup's own key was stored with that recovery key (a Blackout setup that stopped right after creating its backup may not have stored it); a Blackout session you sign in to later, which Blackout can't verify, doesn't add its keys to it. This is tracked as BO-1 in KNOWN_ISSUES.md and is not fixed. We list it here rather than waiting until it is, because a trust page that only mentions solved problems is advertising.

2. Your data, portable, free

Every user can download their account data — profile, linked accounts, social graph, ledger records, scheduled messages, dead-man switches and the public half of their release keys — on any tier, in one click. It does not yet include every record the server keeps.

In the app: Settings → Privacy & data → Download your data. Or over HTTP:

curl -H "Authorization: Bearer $TOKEN" https://api.theblackout.app/v1/data-export

No support ticket, no queue, no tier check. Code: routes/dataExport.ts · usage doc.

This did not exist before 2026-08-10 either. The only export we had returned HTTP 402 below the Coalition tier, which means most users had no way to get their own data. We are not going to describe having fixed that as though it were always true.

Your encrypted messages are not in that file — and that is the encryption guarantee working. The server holds ciphertext and no keys, so it cannot put your messages in a file it generates. If a server-side export did contain your message history, section 1 of this page would be false. Export encrypted history from a signed-in client, which has your keys. Scheduled messages are the one kind of message text the file does hold, because the API keeps that text until the bot sends it.

What we deliberately leave out: credentials (password hash, integration OAuth tokens, vault keys — a portability feature must not become a credential dump), and other people's data. Connections you made are exported in full; inbound ones — your followers, who redeemed your invites — are counted, not listed. Handing you a list of everyone who follows you would export their associations under the banner of your portability.

A gap we disclose in the file itself: follows and profiles are held in server process memory today and reset when the API restarts, so an empty result there may mean the server forgot rather than that you have no connections. Every section of the export carries a durability marker saying which it is.

3. Governance you can audit

Every change to what we promise is recorded, dated, and visible as a diff.

  • Policy changelog — every privacy and monetization commitment, with effective dates. git log -p docs/legal/CHANGELOG.md is the audit trail.
  • How commitments change — the rule is that a policy change and its changelog entry land in the same pull request.

Enforcement is social, and we would rather say so than imply otherwise. Nothing in CI can tell that a diff weakens a promise. What exists is real but narrow: docs/legal/**, this file, and the encryption guard are owned in CODEOWNERS so changes need maintainer review, and guard:room-encryption mechanically protects the one commitment most likely to erode. A determined maintainer could still change a promise without touching the changelog. The protection is that the discrepancy would be discoverable, because every claim on this page points at the code behind it.

Not yet built, and not dated: a cooperative charter — member governance, formal decision rights over policy changes, legal structure. At current scale it would be documentation of a process nobody follows. It is on the roadmap and listed here so the roadmap is part of what you are judging, not a surprise later.

Also honest about status: the Privacy Policy and Terms of Service in this repository are drafts pending counsel review, with unfilled placeholders. They are not in effect, and neither this page nor the policy changelog is a substitute for them. The commitments above are engineering and product commitments backed by code you can read.

The warrant canary is the operator's statement, or there is none. GET /v1/transparency/canary reports a statement only when the operator of the server has issued one, with the date they issued it, and reports it as lapsed once they have not renewed it (after 35 days, unless the operator set another length). The server never writes or renews the statement itself. Until 2026-11-16 it did: it wrote the statement on every request and dated it to the current month, so it could never lapse, and this page called that "live and signed". This page does not say whether a statement is in effect, because only the endpoint can: a page cannot lapse. Where the answer carries a signature, it is made with a key the server holds as it answers, so it shows that the answer came from a holder of that key and not that a person signed anything. The public key sent with the answer proves nothing by itself, and no copy of it is published anywhere else yet.
