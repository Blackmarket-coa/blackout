# Blackout and Forge product/software integration

**Updated:** November 27, 2026
**Status:** Target ownership and handoff map. This documentation does not establish a deployed feature.

## Blackout software map changes

| Native surface | Native everyday use | Advanced Forge surface |
| --- | --- | --- |
| Community settings / Hosting | Community participation and authorized status | Self-host/federation setup and maintenance |
| Go live / Stream settings | Select prepared profile, broadcast, moderate and end session | Owncast/OBS, scene kits, keys, simulcast, separate live/archive outputs and diagnostics |
| Share / stream details | Share result and supported prepared embed | External player/chat embedding and origin/access validation |
| Creator tools / Appearance / Coalition | Apply enhancements, contribute assets, use kits and join activities | Author templates, overlays, plugins, sound/game/quest packs, preview and publish |
| Integrations / Privacy | Routine controls and existing privacy surfaces | Forge automation/technical setup; relevant protection operations connect to Blackmask |

Keep audience, contest/reputation rules, private membership and communication scope. Do not infer live position access or change map location consent from a technical setup action. Project collaboration reuses Blackout services instead of adding a competing messenger.


## Advanced capabilities consolidated into Forge

- Self-host setup, domains/TLS, federation, service configuration, upgrades, logs, backup/restore and diagnostics. The current downloadable Compose blueprint is a starting point, not a remote deployment manager.
- Owncast/OBS setup, saved destinations/keys, simulcast routing, scene/overlay/widget kits, external-origin player/chat embeds, and separate live versus clean archive output.
- Advanced themes, sound/visual assets, widgets/plugins, community/quest/game kits, schemas, compatibility, package publishing, private client releases and licensed remixing.
- Visual recipe and technical API/webhook/RSS configuration, sample-data testing, execution history and controlled retry.

Keep go-live/end-session, prepared-profile selection, moderation, participation, basic clipping, simple uploads/listings, earnings, and applying installed enhancements in Blackout. Coalition and Coliseum remain inside Blackout; shared Matrix/community/media services retain their authority. Project review/collaboration should reuse these services rather than creating a second messenger.

## Creator workflow and blockers

Use native contextual prompts to enter a specific Forge template/project, save/resume work, preview with synthetic data and scoped feedback, package actual bytes, and publish through FBM's registry. Verify checkout/entitlement/redelivery/install and refund states before claiming a complete creator economy.

The checked product wizard holds drafts in component state. The ordinary FBM listing adapter maps metadata and omits artifact payload/upload fields; bytes require the separately connected signed-bundle publish flow. These are priority integration gaps. Do not treat a successful metadata request or a locally rendered preview as product fulfillment.

Add host/device/role testing, reusable package versions, author/license/compatibility display, and an owned asset library in Forge. External website embeds need separate origin/auth and public/private access validation; chat beside a stream inside Blackout is not that complete product.

## Native surfaces

Persistent **Forge — Build, customize & host** near Settings/Privacy; contextual links at Community settings/Hosting, Go live/Stream settings, Share, Appearance/Enhancements, Coalition creator tools, Connected services and authorized project status. Keep essential privacy controls native with appropriate Blackmask links; Forge authors technical profiles without becoming a recipient of private content.

## Shared handoff and evidence requirements

Every supported Forge capability must appear in the source app's Forge hub or have a direct link; important contextual tasks also need their own shortcut. Use a stable capability directory with ID/title, supported apps, required role, runtime/platform support, launch target, status source and return behavior.

Open the specific authorized project/tool. Preserve intent through sign-in/install/denied/unavailable/unsupported-device states; do not claim a web editor exists until implemented. Reauthorize at the destination; use short-lived authenticated references, not raw keys, tokens, private content or Vault records in URLs. Return to the original app and refresh confirmed status. Do not remove a working advanced interface until Forge parity and the complete handoff/return path are verified.

Forge authors/configures; existing domain backends enforce actual resources, access and runtime state. Deployed services continue while Forge is closed. Essential privacy/recovery/accessibility remains available independently of purchases or Forge. Optional enhancements retain one-time ownership direction; no fee or subscription change is made here.
