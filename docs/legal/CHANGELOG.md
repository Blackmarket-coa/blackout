# Policy changelog

Every change to Blackout's **privacy and monetization commitments** is recorded
here, with an effective date and a link to the commit that made it. The git
history of this file is the audit trail: `git log -p docs/legal/CHANGELOG.md`
shows every commitment this project has ever made, when it changed, and who
changed it.

This is deliberately separate from the release changelogs. `/CHANGELOG.md` and
`/docs/changelogs/` are inherited from element-web and generated by `allchange`
from PR metadata — they describe **shipped code**. This file describes **promises
to users**, which change on their own schedule and must not be rewritten by a
tool. Do not put policy entries there, and do not put release notes here.

Entries are newest-first and dated by **effective date**, not merge date. See
[`policy-change-process.md`](policy-change-process.md) for how a change gets
made, and [`../../TRUST.md`](../../TRUST.md) for the user-facing summary of what
these commitments mean.

**Status of the underlying legal documents:** `privacy-policy.md` and
`terms-of-service.md` in this directory are **drafts, not yet in effect**, with
unfilled placeholders pending counsel review (see [`README.md`](README.md)). The
commitments recorded below are engineering and product commitments backed by
verifiable code; they are not a substitute for those documents, and nothing here
should be described as a published privacy policy until that review lands.

## 2026-10-29 — Dead-man releases: what the server keeps, the bot's notice, the export

**Why this entry exists:** a new category of data the server keeps, and a new
plaintext post by the bot. The server side of the dead-man switch release
([`docs/security/release-envelope-2026-10-26.md`](../security/release-envelope-2026-10-26.md))
is built: a switch can hold a message encrypted on the owner's device for the
people named, sealed to their release keys. Arming such a switch stays closed on
every deployment until an operator turns `BLACKOUT_DEADMAN_RELEASES` on, which
no deployment, compose or env file does. This entry was corrected on
2026-10-30, 2026-10-31 and 2026-11-01, before any of it took effect, where the independent
review of the API side found that a sentence here, or in
[`TRUST.md`](../../TRUST.md) §1, was not true; `git log -p` on this file shows
each correction.

### Added

-   **The server keeps, for a switch in the release format,** the encrypted
    message and a commitment to its key, one sealed copy of the key per person
    named and one for the owner, each with the owner's signature, the public
    release key the owner signed with, the account ids of the people named, the
    timer and the owner's label
    ([`packages/api/src/services/deadmanReleases.ts`](../../packages/api/src/services/deadmanReleases.ts),
    migration 106). It cannot read the message, as long as the owner compared a
    safety code with each person named and nobody's app code was altered (in a
    web browser the server supplies that code). It can see who armed what for
    whom, which of three padded sizes the message is, every check-in, when the
    switch fires and who fetched their copy. The content one account can make
    it keep is bounded (its rows are not: a cancelled switch's stay, below):
    20 release switches with content held, 10 arms in 24 hours, 5
    held releases naming one person from one owner and 50 distinct owners
    naming one person, so 250 releases at most
    (`GET /v1/deadman/limits` reports each; exact on one API server against
    requests sent at once; across several replicas a burst of requests can
    exceed them by up to its own size until each replica's arms are
    confirmed by the database and announced to the others). The bound of 50 owners can be filled on purpose, for many
    people at once: one release names up to 64 people and each account
    counts once toward each person it names, so fifty accounts with release
    keys, each with its 20 held switches naming 64 people, keep every other
    owner from naming any of 1,280 people (the owner is refused, 409
    `recipient_limit`, and sees it), in two days, about 26 for each account
    used, while those switches stay armed (one check-in per switch per
    interval, which can be up to 365 days) and for at least 365 days after
    they fire, and neither a person named nor anyone else can clear it
    through the app or the API. The operator chose on 2026-10-31 to count
    owners rather than releases, under which ten accounts did the same
    ([`release-envelope-2026-10-26.md`](../security/release-envelope-2026-10-26.md),
    decision 18). The rows of a cancelled switch stay, blank. Cancelling removes
    the message and the copies from its database (backups aside; across several
    API replicas a re-seal on another replica in the moment the cancel reaches
    it can leave one copy on the cancelled switch, given to nobody, until it is
    removed by the sweep's next pass); 365 days after a switch fires they are removed, at the
    sweep's first pass after that, and the rows stay, saying what the switch
    was, whom it was for and the fingerprint of the key each copy was sealed to,
    and, for each notice, its status and attempts, and its room until that
    person deletes their account.
-   **The bot posts a notice in a room that is not encrypted.** When a release
    switch fires, the Blackout bot makes a "Blackout notices" room for each
    person named who has none yet, and reuses it for later notices, invites
    them as a direct message, and posts one fixed sentence with the release's
    id (the room's alias is an HMAC of the person's Matrix id under a key
    derived from the server's secret, so that a room the homeserver finished
    making after the bot stopped waiting is found rather than made again). In
    the cases [`KNOWN_LIMITATIONS.md`](../../KNOWN_LIMITATIONS.md) lists a
    person can still get an extra room: a slow or interrupted homeserver, or
    the server's background work stopping right after the homeserver made the
    room while the homeserver refuses the alias, can leave an extra one with
    only an invitation in it; and where two copies of the server's background
    work are at work on one person's notices at once, which a claim on the
    person in its database prevents unless one holds it past its time limit,
    and the homeserver refuses the alias, the two can each make the person a
    room and post the notice in each (a copy whose request for the claim
    fails or goes unanswered leaves the person's notices alone). While the
    bot works on a person's notices the server keeps that claim (the account
    id, a random token and an expiry); one left behind by a process that
    stopped or could not give it up stays until the next claim for that
    person replaces it, and for good if their account is deleted first. The notice carries nothing of
    the message, nobody's name, not the owner's
    label. The room is a plaintext service room like the others
    [`TRUST.md`](../../TRUST.md) §1 lists, created so that the homeserver does
    not mark it encrypted (the bot cannot encrypt, so its post is plaintext
    whatever a room's state says), and the sentence says so. The server
    keeps, per notice, the room, how many attempts were made, the last error and
    when it was sent or given up after 30 days. Whether a notice reaches anyone
    depends on the homeserver and the person's client; the release does not
    ([`packages/api/src/services/deadmanReleaseNotifier.ts`](../../packages/api/src/services/deadmanReleaseNotifier.ts)).
-   **The data export lists** a release switch's format, when it fired and its
    notice counts under `deadmanSwitches`, and the releases given to the person,
    each with their own sealed copy and the owner's public key at arming, under
    `deadmanReleases` (`account.deadmanReleases` in the self-service export).
    [`TRUST.md`](../../TRUST.md) §2 says so.
-   **Arming, checking in and cancelling are confirmed by the database** where
    the server keeps its data in one: an arm is answered only once the
    database holds the switch and its copies (otherwise an error, and nothing
    is armed), and a check-in or cancel only once the database has applied it
    to the switch as that server process read it, so one made after the
    switch fired is refused rather than taking the release back. One the
    database does not confirm within 30 seconds is answered as unconfirmed;
    a cancel confirmed late removes the copies when it is. While the database
    does not answer, check-ins are refused, and the server treats that time
    as an outage of its own for the switches it kept from moving: one due
    then gets the 72-hour grace window instead of firing, in the process that
    runs the sweep
    ([`KNOWN_LIMITATIONS.md`](../../KNOWN_LIMITATIONS.md)).
-   **Deleting an account** removes the sealed copies of its unfired release
    switches with their content (whether a switch has fired is decided on
    the database's row, so one that fired on another process stays released
    even where the process handling the deletion had not yet been told of
    it; only where the database does not answer that question in time does
    the deletion go by what that process knew); a fired one keeps its
    content, the copies for
    the people it named and the public key it was signed with, until they are
    removed at the first sweep 365 days or more after it fired, and only the
    owner's own copy and the label go, so that what was
    released stays checkable (a switch armed before
    releases, every switch that exists today, keeps its payload for the people
    it named with no removal date). As a person named on others' switches, the
    account's copies are removed (across several API replicas one sealed to it
    in the moment the deletion reaches another replica can stay until that
    release is cancelled or removed), a notice still owed to it is dropped
    once the deletion is confirmed (one the bot was already sending can still
    arrive, as can the invitation to its notices room it was already making;
    wherever the server keeps its data in a database the confirmation waits
    until the server has tried to write the deletion's changes there, and
    across the API and worker processes the bot can still send a notice
    until then, and after it if the write removing the account's copy fails,
    which is logged, before the deletion's last step has run), and its notice rows forget
    their room (across the API and worker processes through the deletion's
    last step, which is waited for at most 10 seconds and can finish after
    the confirmation; until it does, and for good if it fails, which is
    logged, a notice that was being sent keeps its room). The export of an account includes
    the notice rows about it (`deadmanNotices`), for fired switches.

### Not changed

-   Switches that exist today change status when they fire, as before; nothing
    is released, posted or sent for them.

## 2026-10-26 — Release keys: what the server keeps of them, and the export

**Why this entry exists:** a new category of data the server keeps. Release keys
are the keys the planned dead-man switch release is sealed to and signed with
([`docs/security/release-identities-2026-10-26.md`](../security/release-identities-2026-10-26.md)).
Arming a switch is still closed, so nothing is encrypted for them yet.

### Added

-   **The server keeps the public half of a person's release keys** once they
    publish it from Settings → Release keys: an Ed25519, an X25519 and an
    ML-KEM-768 public key with the person's own signature, the keys they
    replaced, and when
    ([`packages/api/src/routes/releaseIdentities.ts`](../../packages/api/src/routes/releaseIdentities.ts)).
    Any account signed in on the homeserver can read them, and the server sees
    who looks up whom. Deleting the account removes them: for each one a row
    stays with no keys and no account, saying only when it was published and
    replaced. (A copy of the one a release switch was signed with stays with
    that switch once it has fired, until it is removed at the first sweep 365
    days or more after: the 2026-10-29 entry above.)
-   **The private half never reaches the server.** It stays on the devices
    that made it or loaded a recovery file, and in the recovery files the
    person saves; signing out does not remove it from a device. The app's
    publish call sends the six public fields and nothing else
    ([`packages/blackout-sdk/src/release/actions.ts`](../../packages/blackout-sdk/src/release/actions.ts)).
    A web browser runs the app code the server sends it, so this holds for the
    code as published; the desktop and mobile apps carry their own copy.
-   **The data export lists the public halves** (`account.releaseIdentities`),
    and [`TRUST.md`](../../TRUST.md) §2 says so.

## 2026-10-25 — Two gaps between the code and the encryption and logging commitments, closed

**Why this entry exists:** no commitment changes. Two places where the code
contradicted [`TRUST.md`](../../TRUST.md) §1 were found and fixed, and the process
document asks that a closed gap be recorded against the commitment it restored.
The full record, with the other findings fixed alongside, is
[`docs/security/api-findings-triage-2026-10-25.md`](../security/api-findings-triage-2026-10-25.md).

### Changed

-   **The API message endpoint no longer claims encryption or signatures it does
    not do.** `POST /v1/messages/:channelId`
    ([`packages/api/src/routes/messages.ts`](../../packages/api/src/routes/messages.ts))
    stores the text readable on the server at every `stegoTier`, as §1 has
    always said. Until this date a request with `stegoTier: 2` had its text
    XOR-ed with the first sixteen characters of a server-minted random string
    and the row labelled `encryptionAlgorithm: 'e2e'`, `isEncrypted: true`; a
    request with `sign: true` stored a URL-encoded copy of the text as its
    "signature". The endpoint now reports `isEncrypted: false` on every row, old
    rows included, stores tier-2 text as written, and answers
    `400 signing_unavailable` to a request for a signature. The helpers behind
    the labels (`encryptE2E`, `decryptE2E`, `signMessage`, `verifySignature`)
    were removed from `@blackout/core` so nothing can build on them. Visible to
    a client of that endpoint: the Expo scaffold in `packages/mobile` sends
    `stegoTier: 2` and now reads its text back as written.
-   **The dead-drop appservice's legacy queue no longer logs message text.** Its
    flush
    ([`apps/deaddrop-appservice/src/index.mjs`](../../apps/deaddrop-appservice/src/index.mjs))
    wrote each queued message's body and sender to the console, against §1's
    "nothing logs your messages". It now logs the body's byte length and whether
    the room anonymizes senders. Not user-visible: only an operator reading the
    appservice's log saw it, and the v1 opaque-envelope path the clients use was
    never affected.

### Rationale

-   A label that says encrypted when the server can read the text is the defect
    this file exists to prevent, whichever direction it points. The helpers were
    removed rather than repaired: an XOR against a value the server holds is not
    something to make work.

## 2026-09-20 — Coalitions: cross-posting, inbound replies, attribution

**Why this entry exists:** this work introduces a new category of data
collection and retention — third-party reply text and engagement counters read
back from external platforms — and stores platform credentials on a coalition's
behalf, which the process document lists as requiring an entry.

Nothing in [`TRUST.md`](../../TRUST.md) becomes less true. The encryption and
monetization commitments are untouched, and the one place this work meets an
existing promise — §2's rule that inbound connections are _counted, not listed_
— is exactly the shape attribution takes below: founders see totals per
channel, never a list of people. Every capability here ships behind a flag that
defaults **off**; the three flags are named at the end.

### Posting out

-   **Nothing is posted to an external platform without an explicit
    per-campaign, per-platform, per-member opt-in.** An absent opt-in row means
    off; there is no opt-out default and no coalition-wide switch that enrols
    people. Rule 1 of the module header and `setOptIn` in
    [`coalitionSync.ts`](../../packages/api/src/services/coalitionSync.ts).

-   **Automated announcements come only from accounts the coalition itself
    connected — never from a member's personal account unattended.** The
    milestone sweep uses `authMode: 'shared'` connections only. Campaign types
    that ask the public for money or goods (`drive`, `goods_drive`,
    `mutual_aid`) are never auto-announced; a member can still share them by
    hand. `ANNOUNCEABLE_TYPES` and the `'shared'` check in
    [`coalitionAutoCrosspost.ts`](../../packages/api/src/services/coalitionAutoCrosspost.ts).

-   **Automation is limited to platforms whose terms sanction it, and the
    record of those terms lives in code so that a change to it is a visible
    diff.** `COALITION_PLATFORM_POLICY` in
    [`coalitionNetwork.ts`](../../packages/core/src/coalition/coalitionNetwork.ts)
    records, per platform: the terms (name and URL), the automation basis, the
    access tier, whether an agreement is required, whether one has been accepted
    (`null` everywhere today), the rate limit with its source, and a `reviewedOn`
    date (2026-09-20). `platformCanAutomate` derives the answer from that record
    and fails closed. Today: X is **not** automated, because its paid developer
    agreement has been accepted by nobody (`agreement_unsigned`) and no adapter
    exists (`no_adapter`); Discord posts only through a coalition-owned incoming
    webhook — a member's personal token would be self-botting and is refused at
    connection time (`authModes: ['shared']`); Bluesky posts by app password and
    Mastodon by application token under the instance's terms; Instagram and
    TikTok are share links a person completes. Adapters:
    [`coalitionPlatformAdapters.ts`](../../packages/api/src/services/coalitionPlatformAdapters.ts).

### Platform credentials

-   **Credentials a coalition connects are stored as AES-256-GCM envelopes
    bound to their connection, decrypted only to post or to read back, never
    returned by the API, revocable per connection, and rotatable by key id.**
    The envelope is [`secretBox.ts`](../../packages/api/src/services/secretBox.ts)
    under `LINKED_ACCOUNT_ENCRYPTION_KEYS`; the AAD ties each secret to
    `coalition_connection:{coalitionId}:{platform}` or
    `coalition_member_connection:{coalitionId}:{userId}:{platform}`
    ([`coalitionPlatformAdapters.ts`](../../packages/api/src/services/coalitionPlatformAdapters.ts)),
    so a ciphertext cannot be replayed against another connection. Only the
    posting adapter and the inbound poller decrypt. The routes
    `DELETE /v1/coalitions/:id/connections/:platform` and
    `DELETE /v1/coalitions/:id/connections/me/:platform` in
    [`routes/coalitions.ts`](../../packages/api/src/routes/coalitions.ts)
    revoke; `revokeMemberLinks` in
    [`coalitionConnectionCustody.ts`](../../packages/api/src/services/coalitionConnectionCustody.ts)
    drops the credential from the row.

    **Said plainly: the server operator holds the key.** This is server-side
    encryption at rest, not end-to-end encryption, and must not be described as
    E2EE. The server has to be able to post and poll on the coalition's behalf,
    so the secret has to be usable server-side. Recorded as accepted risk R8 in
    [`THREAT_MODEL.md`](../../THREAT_MODEL.md).

### Replies from other platforms

-   **Reply text from other platforms is quarantined: invisible until a
    coalition moderator approves it.** A coalition may instead choose `'open'`
    for its own mission (replies land approved) or `'off'` (reply text is
    refused outright); the default is `'moderated'`. The external author is
    display text — `"Ada via Discord"` — with no Blackout account, profile, or
    permission. Author is clipped to 120 characters and content to 2000; a post
    accepts at most 500 replies and refuses further arrivals; a reply must
    arrive on the platform the post went out on; duplicate origin ids are
    ignored. Approve only from pending, reject from pending or approved,
    rejected is terminal. A platform moderator (`BLACKOUT_ADMIN_USERS`
    allowlist) can remove any reply with
    `POST /v1/coalitions/:id/externals/:activityId/takedown`; the resulting
    event carries ids and the reason only, never the text. Approved replies are not
    served for an archived or taken-down coalition. `ingestExternalActivity`,
    `moderateActivity`, `takeDownExternalActivity` and `listApprovedActivity`
    in [`coalitionSync.ts`](../../packages/api/src/services/coalitionSync.ts);
    routes in [`routes/coalitions.ts`](../../packages/api/src/routes/coalitions.ts).

-   **Quarantined reply text is retained for a bounded time, then purged.**
    Pending replies are held 30 days from receipt; rejected replies 30 days
    from the decision (else receipt); approved replies 365 days from receipt.
    The windows are `BLACKOUT_COALITION_EXTERNAL_RETENTION_PENDING_DAYS`,
    `_REJECTED_DAYS` and `_APPROVED_DAYS` (positive integers; anything else
    falls back to the default). A daily sweep enforces them and runs whether or
    not inbound sync is enabled — turning the feature off stops new rows, it
    does not excuse the old ones. `BLACKOUT_COALITION_EXTERNAL_RETENTION_SWEEP=0`
    disables the timer and `..._INTERVAL_SECONDS` changes its cadence; a
    deployment that disables the sweep must not enable inbound sync
    ([`THREAT_MODEL.md`](../../THREAT_MODEL.md) §8, criterion 8). The sweep
    never touches engagement counters and logs counts only.
    [`coalitionExternalRetention.ts`](../../packages/api/src/services/coalitionExternalRetention.ts),
    [`coalitionExternalRetentionScheduler.ts`](../../packages/api/src/services/coalitionExternalRetentionScheduler.ts),
    registered in [`backgroundLoops.ts`](../../packages/api/src/backgroundLoops.ts);
    variables documented in [`.env.example`](../../packages/api/.env.example).

-   **Engagement is stored as numbers only.** Likes, reshares, reply totals and
    link clicks land in `coalition_campaign_engagement` as integers — nobody
    wrote them and they name nobody. The numbers/words split is the header of
    [`coalitionInboundSync.ts`](../../packages/api/src/services/coalitionInboundSync.ts);
    the table is
    [migration 098](../../packages/api/src/db/migrations/098_external_engagement.up.sql).

### Attribution

-   **Share links carry a signed token that identifies the campaign, the
    channel, and — for a manual share — the member who shared. It never
    identifies the visitor.** The token is minted before any visitor exists,
    one per share, and expires after 90 days. No cookie, IP address, IP hash,
    fingerprint or user agent is recorded for attribution. The client holds the
    token in `sessionStorage` (key `blackout.coalition.ref`) and replays it only
    if the visitor goes on to act. Founders see totals per channel, via
    `GET /v1/coalitions/:id/campaigns/:campaignId/attribution`, and never a
    list of people — the same rule TRUST.md §2 applies to followers and invite
    redemptions. HMAC-SHA256 under `BLACKOUT_ATTRIBUTION_SECRET`, falling back
    to `JWT_SECRET_PRIMARY`, in
    [`coalitionAttribution.ts`](../../packages/api/src/services/coalitionAttribution.ts);
    the counters table is
    [migration 099](../../packages/api/src/db/migrations/099_campaign_attribution.up.sql);
    the landing page is
    [`CampaignLandingPage.tsx`](../../apps/blackout-client/src/app/features/coalitions/CampaignLandingPage.tsx).

### Flags

-   **Everything above ships behind flags that default off.**
    `BLACKOUT_COALITION_CROSSPOST_ENABLED` opens outbound manual sharing;
    `BLACKOUT_COALITION_AUTOPOST_ENABLED` opens milestone announcements from the
    coalition's shared accounts; `BLACKOUT_COALITION_EXTERNAL_SYNC_ENABLED`
    opens the inbound poller and ingestion. Each is read in
    [`coalitionSync.ts`](../../packages/api/src/services/coalitionSync.ts),
    [`coalitionAutoCrosspost.ts`](../../packages/api/src/services/coalitionAutoCrosspost.ts)
    and [`backgroundLoops.ts`](../../packages/api/src/backgroundLoops.ts), and an
    unset variable means off. Inbound sync is not sequenced behind BO-1: it moves
    public text between public platforms and makes no confidentiality claim
    ([`TRANSMUTATION_NOTES.md`](../../TRANSMUTATION_NOTES.md) §5); its operator
    preconditions are stated in `inboundSyncEnabled`.

**What this does not change:** the encryption commitments (E2EE never behind a
paywall; every private room and DM encrypted by default), what a tier is allowed
to gate, and the deliberately-unencrypted room list are all untouched. Nothing
here weakens a prior commitment. For the sequencing, gates and platform record,
see [`ECOSYSTEM_WIRING.md`](../coalitions/ECOSYSTEM_WIRING.md) §External sync
sequencing; for the adversary and residual-risk analysis, see
[`THREAT_MODEL.md`](../../THREAT_MODEL.md) (A12, §5 asset rows, R8–R9).

## 2026-08-10 — Initial record

The first entry. It establishes the current commitments as a baseline so that
every later change is visible as a diff against something. It is a _record_ of
existing behaviour, not a set of new promises: each item below links to code you
can check today.

### Privacy and encryption

-   **End-to-end encryption is never behind a paywall, on any tier, ever.**
    Verifiable: the complete catalogue of paid feature gating is the seven tier
    tables unioned in
    [`packages/blackout-protocol/src/entitlements/bundles.ts`](../../packages/blackout-protocol/src/entitlements/bundles.ts)
    — none of them contains an encryption key, so there is no mechanism by which
    encryption could be sold.

    This is the commitment most likely to come under commercial pressure, and the
    one this changelog exists to protect. Weakening it requires an entry here with
    a visible diff.

-   **Every private room and direct message is end-to-end encrypted by default.**
    Effective from this date; previously true only on some paths. Enforced by a
    required compiler-checked flag in the API and by
    [`pnpm guard:room-encryption`](../../tools/ci/check-room-encryption.mjs) in CI.
    See [the 2026-08-10 encryption audit](../audits/2026-08-10-encryption-audit.md)
    for what was broken and what changed.

-   **Some rooms are deliberately not encrypted, and we name them.** Publicly
    joinable rooms, and the service rooms the Blackout bot posts into (marketplace
    vendor/order/ledger rooms, `#bugs`, the standing public rooms). The bot has no
    Megolm implementation and cannot post into an encrypted room; encrypting these
    would break them rather than protect them. The current list is in
    [`TRUST.md`](../../TRUST.md) and changes to it belong in this changelog.

-   **No bot or moderation tool can read encrypted room content.** The server bot
    has no timeline-read capability at all — not restricted, absent.

-   **No server-side log, error report, or analytics captures message content.**
    There is no PostHog, Segment, or session-replay integration in the product.

-   **Calls and townhall media are not covered by message encryption today.**
    Transport is TLS; per-call media encryption is in progress. Recorded here
    because it is the kind of gap that is easy to leave out of marketing copy. See
    [`THREAT_MODEL.md`](../../THREAT_MODEL.md) §7 R2.

-   **Privacy-enhancing features beyond encryption are tiered.** Tor transport,
    decoy traffic, image perturbation, persona compartments, dead-drop anonymity
    padding and decoys, mesh transport, and active defense are paid. We say "E2EE
    is never paywalled", which is true; we do not say "privacy is never
    paywalled", which would not be.

### Monetization

-   **Nothing is being charged as of this date.** The monetization surface ships
    in a default-unlocked posture: the catalog is visible but every premium feature
    resolves as owned. Going live is a deliberate flip, gated on legal/compliance
    sign-off. See
    [`../operations/MONETIZATION_GO_LIVE.md`](../operations/MONETIZATION_GO_LIVE.md).

-   **Four tiers: Free, Signal, Coalition, Sovereign.** Free is a usable product,
    not a trial — baseline private encrypted communication with no expiry. Defined
    in
    [`consumerTiers.ts`](../../packages/blackout-protocol/src/entitlements/consumerTiers.ts).

-   **What paid tiers add is capability, not un-crippling.** Paid features are
    substantively different code paths, not switches that re-enable something
    already written. Stated in each entitlement family's own source.

-   **Prices are not defined in this repository.** The catalog lives in the Free
    Black Market service. Price changes are not policy changes and do not require
    an entry here; changing _what a tier is allowed to gate_ does.

-   **Self-service transparency and the warrant canary are free at every tier.**
    `GET /v1/transparency/me` and `GET /v1/transparency/canary`, the latter
    Ed25519-signed.

### Data portability

-   **Every user can export everything the server holds about them, free, on any
    tier.** Available from **Settings → Privacy & data → Download your data**, and
    over HTTP as `GET /v1/data-export`. It returns portable JSON in a single
    request, has no entitlement check, and adding one would be a policy change
    requiring an entry here.

    This closes a gap that existed earlier the same day: the only export was
    `GET /v1/transparency/audit-export`, which returns HTTP 402 below the
    Coalition tier, so most users had no way to retrieve their own data. That
    endpoint remains a tiered org-scoped capability; the personal export is
    separate and free. See
    [`docs/features/data-export.md`](../features/data-export.md).

-   **The export does not contain your encrypted messages, and it says so.** The
    server holds ciphertext and no keys, so it cannot include them — a
    server-generated export that did would contradict the encryption commitment
    above. The payload states this and points at the client-side export, which
    has the keys.

-   **Credentials and other people's data are withheld.** Password hashes,
    integration OAuth tokens, and vault keys are excluded — they are credentials,
    not user data. Inbound social edges (your followers, who redeemed your
    invites) are exported as counts rather than lists, because naming them would
    export other people's associations under the banner of your portability.

-   **Known gap, disclosed in the export itself:** follows and profiles are held
    in server process memory and reset on restart, so an empty result there may
    mean the server has no current record rather than that you have no
    connections. Each section carries a `durability` marker saying which it is.
