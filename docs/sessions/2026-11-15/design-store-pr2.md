## 1. Scope and the PR 3 boundary

**In PR 2 (approved by the operator, 2026-10-31):**

1. The security-table upserts (O3) stop replacing whole rows: a create inserts only where no row
   has its key; an update writes only the columns the call changed and inserts only where the
   method is a create-or-update (§2.1's three insert modes); a one-way column (revoked, consumed,
   used, burned, claimed, opened, left, lifted, read, processed, superseded, delivered) can be set
   only where it is still unset, so Postgres keeps the first writer; the logout-everywhere cutoff
   never moves back. **61 spec lines** (§3: 26 creates, 30 patches — one of them a new store method,
   `resetUserPassword`, §3.1 — `revokeSession`, 4 new S7 specs).
2. The deleted account's token (O6): the auth middleware refuses a token whose account does not
   exist. No migration. The deletion's own denylist write (S8) **moves before the delete** so it
   lands, is announced and sticks (§4.5); it is not removed.
3. A real-PostgreSQL 16 CI job runs `store-cross-process` (§5).
4. The four unspecced writers (O8/S7) get specs; the nullable conflict key is solved without a
   migration (§6).
5. D1 is recorded as the behaviour wanted (§7).

**Hard constraints, and where each is met:** Postgres keeps the first writer for every one-way
column (§2.3, §3); a stale copy never reverts a password (§3 `users`: a compare-and-set on the
change path, and a reset path that needs none), re-inserts a deleted account (`patch` never
inserts for a row the mirror held, §2.1), un-revokes or un-consumes (§2.3), overwrites a
rejection (§3 moderation) or revives old ciphertext (§3 vault, linked accounts, release
identities, scheduled messages); a refused write's mirror re-reads the row through PR 1's
`onRereadKeys` → `refreshKeys` path (§2, every kind); a committed change is announced (`'k'`
inside the transaction for targeted ops, `'u'` after commit for upserts, nothing for a refused
write because Postgres did not change); no legitimate write is dropped to make that true (§3,
"the prior-absent rule, per table": counters add, a relink lands, a password reset lands, the one
remaining loss is pre-existing and named); no write reconciles a table; every write stays in the
write-behind queue; every new behaviour has a test that fails without it on PGlite and on
PostgreSQL 16 (§8); U1's allowlist shrinks from 23 to 19 (§6); the record, `KNOWN_LIMITATIONS.md`,
both deploy comments and the store header are made true again (§7).

**Where PR 2 stops.** PR 2 makes Postgres keep the right row and every mirror converge to it,
without an awaited write: the request that raced has **already been answered** on the loser's
process (200), and PR 2 only makes its effect not land in Postgres and its mirror re-read. The one
awaited Postgres access PR 2 adds is a **read**: the middleware's keyed `SELECT` on a mirror miss
(§4), run on the store's FIFO apply chain, bounded and fail-closed.

**Where PR 3 starts (not in scope):** the answer itself waits for Postgres. Awaited conditional
writes for the five consumes, the refresh-token rotation (with `pg_advisory_xact_lock` on the
family in both the rotation and the family revoke, O2), the invitation admission claim and
use-count increment, the bounty accept (O1); `flushRuntimeStoreWrites` returning per-op outcomes;
the orphan successor a refused rotation leaves live (X26 asserts it so the record stays honest);
turning the password change's refused compare-and-set into a 409 instead of a late re-read (Q5).
PR 2's `patch` statements are the statements PR 3 will await; PR 3 changes how they are waited
for, not what they say.

**Outside both:** the dispatcher sending a message a stale worker still lists as pending
(check-then-act, O1); a process that never hears a change (O4: the boot gap, a half-open
listener), including a deleted account's token on such a process (§4.4); `deadmanSwitches`
(v46 rebuilds those writes as conditional statements with `enqueueCall` and
`switchWritesInFlight`; PR 2 leaves its three specs as they are and names v46 as the owner); the
whole-row tables outside O3's list, two of which hold moderation state and are named in §3 so the
record does not read as covering them.

## 2. The kinds

PR 1 left two spec kinds (`pgDescriptors.ts:574-576`): `upsert` (the record the method returned,
whole, one statement, `'u'` after commit, no `RETURNING`) and `targeted` (fixed statements, one
transaction, `'k'` inside it, `RETURNING` keys, re-read of the symmetric difference between the
keys the statements returned and the keys the call changed: `writeBehindQueue.ts:319-320`,
`store.ts:8756-8764`). PR 2 adds **no third top-level kind**. It adds:

-   on the `upsert` kind: v46's `insertOnly` and `guardOf` (verbatim), plus two behaviours for
    every upsert: **G1**, a call that wrote no key queues nothing, and **G2**, a refused upsert
    re-reads its key and sends no `'u'`;
-   on the `targeted` kind: a new `TargetedStep` op `patch`, and two options on `upsertEach`
    (`onConflictWhere`, `conflictTarget`), the second also taken by `patch`'s insert branch;
-   one declarative table list, `STICKY_COLUMNS`, read by `patch` and checked at boot.

Every converted update therefore inherits PR 1's transaction, in-transaction `'k'`, boot
`PREPARE` (U3), capture (U6) and re-read; every converted create inherits v46's shape and merges
with it line for line.

### 2.1 `patch` (new `TargetedStep` op, `pgWriter.ts`, in PR 1's targeted section below `hydrateMap`)

```ts
| (StepBase & {
      op: 'patch';
      /** Compare-and-set: columns that must still hold the value the mirror held before the call (guardExpr: ms timestamps, jsonb, NULL-safe). */
      cas?: string[];
      /** A literal predicate over this table's columns, ANDed to the key match. May use $n after the SET and key parameters when `params` is given. */
      where?: string;
      params?: (ctx: StepContext) => readonly unknown[];
      /** Counter columns written as `c = c + (after - before)` instead of `c = after`; an absent prior value counts as 0. */
      delta?: string[];
      /** Sticky columns this step may set even where the stored row already has them: `c = COALESCE(c, $n)` replaces the `c IS NULL` predicate. */
      keepStored?: string[];
      /**
       * What to do with a key the call added (the mirror had no row). Default: a bind error (a patch
       * spec on a creating method is a spec bug, made loud). 'nothing': insert, or leave the stored
       * row as it is (a true create). 'add': insert, or add this record's `delta` columns to the
       * stored row and touch nothing else (needs `delta`). 'replace': insert, or overwrite the
       * stored row's columns this record carries, keeping its id and created_at.
       */
      insertWhenAbsent?: 'nothing' | 'add' | 'replace';
      /** The insert branch's arbiter, replacing `(<conflict columns>)` after ON CONFLICT: a column list, optionally with a partial-index predicate. */
      conflictTarget?: string;
  })
```

`TableDescriptor` gains `sticky?: string[]` (`pgWriter.ts:84-96`), filled from `STICKY_COLUMNS`
in `TABLE_DESCRIPTORS` (`pgDescriptors.ts:556-566`, one line).

**Binding** (`bindStep`, `pgWriter.ts:473-535`, from `ctx.changed(map)`, which `captureWrites`
already supplies, `store.ts:8424-8470`, `8596-8632`), one statement per changed key.

**The diff rule, exactly (critique round 2, gap 7).** The two records are compared **as rows**:
`recordToRow(plan, before)` and `recordToRow(plan, after)` (`pgWriter.ts:121-130`), which emit a
column for every **own property** of the record that has a column, serialized by `serializeValue`
(`:62`: an own `undefined` and an own `null` both become `NULL`; `''` becomes `NULL` on a nullable
column). So:

-   A column in **both** rows: changed when the serialized values differ (`!==` on the serialized
    scalar; arrays and `jsonb` strings compared by `JSON.stringify`). Own `undefined` versus own
    `null` is **not** a change (both are `NULL` after serialization).
-   A column in **after's row but not before's**: before lacked the own property — a hydrated copy
    (`defaultFromRow` drops every `NULL` column, `:110-118`) or an in-process record created without
    the field (`createScheduledMessage` sets no `lastError`, `2264-2278`) — and after has an own
    value. **A change**, whatever the value, `NULL` included: `markScheduledMessageDelivered`'s
    `lastError: undefined` and `formattedBody: undefined` (`2312-2325`, an own property on purpose,
    `2305-2310`) and `tripCanary`'s `lastTripUserAgent: userAgent ?? null`
    (`services/activeDefense.ts:72-80`) bind `SET c = NULL`, which is the method's intent and is
    harmless where Postgres already holds `NULL`.
-   A column in **before's row but not after's**: the method dropped a field the prior record had.
    **A bind error** (logged and counted lost by the wrapper, `store.ts:8554-8567`): a patch carries
    every column its prior row had, and a method clears a column by setting the field to `undefined`
    or `null`, not by omitting it. No PR 2 method does this (every patched method spreads `existing`;
    the critique checked each body); U6's one call per spec (§8) makes a future method's mistake a
    red test, not a silent `NULL`. Four `OVERRIDES` have a custom `toRow` (`coalitionRings`,
    `coalitionEvents`, `sellerLocations`, `coalitionAidPosts`, `pgDescriptors.ts:188, 233, 288, 327`);
    none is a `patch` table, and a custom `toRow` runs on both records alike anyway.
-   A column with no field in either record, or a field with no column (`emailVerifiedAt`, `result`,
    `resolvedAt`), is never in the list.
-   A `delta` column is handled by the delta rule below, not by the comparison.

**No changed column → no statement.** This is what silences the unchanged-return methods of O3
that are updates (`markUserEmailVerified` on a verified account, `consumeRefreshTokenForRotation`
on a rotated token, `revokeInvitationToken`, `markBurnerIdentityBurned`,
`markCoalitionNotificationRead`, `openDeadDrop` when already done).
`markUserEmailVerified` binds nothing on **every** call, not only on a verified account: its one
changed field, `emailVerifiedAt`, has no column (§3.1), so the wrapper queues nothing (an op is
enqueued only when a statement was bound, `store.ts:8645`). That guard stays: an op with no
statement would commit an empty transaction that returns no key, and PR 1's symmetric-difference
re-read (`writeBehindQueue.ts:319-320`) would copy Postgres's row, which lacks the field, over the
writer's own mirror and wipe the verification where it was set. U6 declares the method as binding
nothing rather than expecting its keys to be queued (§8; critique round 3, gap 1).

**The sticky rule at bind.** For a sticky column (§2.3) the SET writes it only where it is still
`NULL` (`s IS NULL` in the `WHERE`), unless the step lists it in `keepStored` (`COALESCE`). A patch
whose diff writes a sticky column to `NULL`:

-   when before's row held a **non-NULL** value → **a bind error** (a revert attempt by
    construction; nothing in the tree does this);
-   when before's row **lacked** the column (a hydrated copy) and after has an own `null` → the
    column is **dropped from the SET** (a no-op by construction: Postgres holds `NULL`, or holds a
    value the `s IS NULL` predicate would protect anyway). No PR 2 method produces this either; the
    rule is stated so `bindStep` has no undefined case.

**The delta rule.** For a `delta` column `c`: the bound value is `after[c] - before[c]`, where a
record **lacking the field counts as 0** (records may lack it: `rotateBurnerIdentity` reads
`existing.rotationEpoch ?? 0`, `945-958`; all five delta columns are `NOT NULL DEFAULT 0`:
`021:199`, `066:8`, `074:13`, `098`, `099`). `bindStep` throws when the difference is not a finite
number (a string, `NaN`, `Infinity`): a bind error, logged and counted lost by the wrapper as every
bind error is, never a `NaN` sent to Postgres. A delta of 0 is not a change (the column is left out
of the statement).

**Prior absent, after present** → by `insertWhenAbsent` (SQL below). `'add'` requires `delta`
(else `compileStep` throws); a delta column absent from `after` is inserted as 0. Without the
option: a bind error, logged and counted (U8 keeps this out of production, §8).

**Prior present, after absent** → a bind error (a patch never deletes).

**SQL (update branch):**

```sql
UPDATE t SET c1 = $1, c2 = c2 + $2 /* delta */, s1 = COALESCE(s1, $3) /* keepStored */
WHERE <keyCondition(k, 'k', '$4')>            -- plain = , or IS NOT DISTINCT FROM for a nullable key (pgWriter.ts:361-365)
  AND s2 IS NULL                              -- for each sticky column the SET writes that is not in keepStored
  AND <guardExpr(cas_col, 'cas_col', '$5')>   -- for each cas column, bound to the PRIOR record's value (pgWriter.ts:334-347)
  AND <where literal>
RETURNING <keys>
```

**SQL (insert branch, by mode):**

```sql
-- 'nothing' (a true create; the row another process already wrote stands):
INSERT INTO t (cols) VALUES ($1..$n) ON CONFLICT (keys | <conflictTarget>) DO NOTHING RETURNING <keys>
-- 'add' (counters: the two processes' credits add; nothing else is touched):
INSERT INTO t (cols) VALUES ($1..$n) ON CONFLICT (keys) DO UPDATE SET d1 = t.d1 + EXCLUDED.d1, d2 = t.d2 + EXCLUDED.d2 RETURNING <keys>
-- 'replace' (a relink: every column the record carries except the keys, id and created_at):
INSERT INTO t (cols) VALUES ($1..$n) ON CONFLICT (keys) DO UPDATE SET c1 = EXCLUDED.c1, …, id = t.id, created_at = t.created_at RETURNING <keys>
```

`'nothing'` is `buildTargetedUpsertSql(plan, columns, undefined, { insertOnly: true, conflictTarget })`;
`'replace'` is `buildTargetedUpsertSql(plan, columns, { id: 't.id', created_at: 't.created_at' })`
(the aid-post arbiter's shape, §6; the two keep-columns are added only when the table has them);
`'add'` is a new small builder `buildInsertOrAddSql(plan, columns, deltaColumns)` beside
`buildTargetedUpsertSql` (`pgWriter.ts:368-386`), whose `DO UPDATE SET` names **only** the delta
sums. `'add'` and `'replace'` set `BoundStatement.merges` (`pgWriter.ts:297-308`): the row
Postgres keeps differs from the record bound (summed counters; the stored `id`), so the returned
key is re-read into the writer's mirror as the mesh `seen_by` union is today (`MESH_SEEN_BY_UNION`,
`pgDescriptors.ts:730-733`). `conflictTarget` is used once on a `patch`, for external replies
(§3.5): with a partial-index arbiter, a row the index predicate does not cover (an id-less reply)
inserts as a plain row, and a row it covers converges on the stored one.

`checkSql` for the boot `PREPARE` (`compileStep`, `pgWriter.ts:395-470`; `compileTargetedSpecs`,
`store.ts:8660-8716`) names every non-key column in the SET with its cast (as `upsertEach`'s
does), every `delta`, `cas`, `keepStored` and sticky column, and the `where` literal, so a column
the live table lacks refuses the boot (U4's rule; a missing table still skips the step, U4b).
`delta` columns must be numeric (`udt_name` int2/int4/int8/numeric) or `compileStep` throws.
`compileStep`'s "where uses no parameter" check applies to the combined predicate, whose key
match always carries one, so a literal such as `status = 'pending'` is allowed on a `patch` (it is
still refused on `updateWhere`/`deleteWhere`). For a step with `insertWhenAbsent` the insert
branch's all-columns statement (with its `conflictTarget`, so an arbiter no index backs refuses
the boot) is `PREPARE`d as a second check statement, carried in a new optional field
**`CompiledStep.insertCheckSql?: string`** (today `CompiledStep` has the one `checkSql`,
`pgWriter.ts:310-319`), set by `compileStep` for that case only. Both loops that `PREPARE` change
(critique round 3, gap 4): `compileTargetedSpecs` (`store.ts:8696-8708`) prepares `c.checkSql`
and then `c.insertCheckSql` when present, naming the one that failed in its error; U3
(`test/pg-writer-targeted.integration.test.ts:245-267`) prepares both too, applies
`restrictsByParameter` (`:74-77`: `UPDATE|DELETE … WHERE … $n … RETURNING`) to `checkSql` only —
the insert statement is exempt, an `INSERT` being bounded by its conflict target, not a `WHERE` —
and asserts that a step has `insertCheckSql` exactly when it is a `patch` with `insertWhenAbsent`.
Chosen over checking the insert branch some other way because it leaves `checkSql`'s contract
("as `PREPARE`d at boot and, except for `upsertEach`, as run") and U3's rule unchanged for every
existing step; folding both branches into one statement through a data-modifying CTE would start
with `WITH` and fail that rule, and checking the insert branch only in U3 would lose the boot
refusal of an arbiter no index backs. Merge cost: §2.6.

**Not `required`.** A refused patch (0 rows: the row is gone, the `cas` did not hold, a sticky
column was already set, the `where` was false) does **not** roll the op back. Its key is in
`touched` and not in `returned`, so PR 1's symmetric-difference re-read
(`writeBehindQueue.ts:319-320` → `store.ts:8756-8764` → `refreshKeys`, `8836-8871`) puts
Postgres's row into the writer's mirror or removes the key when the row is gone (`8864-8866`).
New: `BoundStatement.refusable?: true`; `attemptTargeted` (`writeBehindQueue.ts:325-375`) counts
`dbTargetedWriteConflictsTotal{map, method}` and logs `db_targeted_write_conflict` for a
refusable statement that returned no row, without rolling back — the same counter X8b asserts
for a bounty gate. `required` is not used on any PR 2 statement: an op with several statements
(a `keepStored` erase plus a status move, or a future multi-row patch) must not lose its other
rows to one refusal.

**Announcement.** Keys the statements returned go out as `'k'` inside the transaction
(`attemptTargeted`, `writeBehindQueue.ts:353-358`; with the in-process test hub, after commit,
`294-299`). A refused key is announced by nobody: Postgres did not change, and the winner's own
write was announced when it committed.

**Spec helper** (`pgDescriptors.ts`, after `USER_AUTH_ARTIFACTS`, inside the hunk that already
conflicts with v46, so no new hunk):

```ts
/** Write only the columns the call changed, to the one row it changed; a one-way column only where still unset; never deletes. */
const patch = (
    map: string,
    o: {
        cas?: string[];
        where?: string;
        params?: Params;
        delta?: string[];
        keepStored?: string[];
```

Defined in **C3**, with its first callers, not in C2 (critique round 3, gap 2): the spec helpers
are non-exported `const`s (`pgDescriptors.ts:578-579`), `@typescript-eslint/no-unused-vars` is
`'error'` with `varsIgnorePattern: '^_'` (`eslint.config.js:43-51`), and a helper with no caller
fails gate 1 (`pnpm lint`, `--max-warnings=0`). C2's tests write their specs as literals
(`{ kind: 'targeted', steps: [{ op: 'patch', … }] }`) through `withSpec`. The same holds for
`insertIfAbsent` (§2.2).

### 2.2 `insertIfAbsent` and `guardOf` on the `upsert` kind (v46's, verbatim), with G1 and G2

**Departure** from attack-first, which put creates on a targeted `insertOnly` op. Reasons, from
the tree: (a) v46's `insertIfAbsent(map)` (`v46 pgDescriptors.ts:593`) is the same word for the
same thing, and adopting it verbatim means its two spec lines, its `enqueueUpsert(mapName,
record, guard?, insertOnly)` (`v46 writeBehindQueue.ts:88-101`) and its
`upsertRecord(client, plan, record, guard?, insertOnly)` (`v46 pgWriter.ts:176-204`) merge with
no edit; (b) a create on the upsert kind keeps its `NOTIFY` after commit, so O14 (a failed
in-transaction `NOTIFY` fails the write) does **not** reach `createUser` — with a targeted create
a `NOTIFY` failure would fail the account `INSERT` after `/register` had already issued the
session, and the middleware check (§4) would then refuse that account on every other process;
(c) 26 fewer U6 cases (U6 requires one call per targeted spec,
`store-spec-coverage.integration.test.ts:466-472`); (d) G1 gives "changed-only" to the upsert
kind anyway, so the five idempotent creates among O3's eleven (`markGreeted`,
`markBillingWebhookEventProcessed`, `addCircleEdge`, `joinVoiceRoom`, `applyVoiceRoomSanction`)
queue nothing when they return an existing record. What the targeted form would have added, an
in-transaction `'k'` for creates, is worth less than (b): a create a replica misses is found by
the middleware's miss-path read.

Shapes (v46's names and parameter positions, `e9556d76dd`):

```ts
export type MutatorSpec =
    | {
          kind: 'upsert';
          map: string;
          /** v46: record fields from the call's arguments that the stored row must still hold for the update to apply. */
          guardOf?: (args: unknown[]) => Record<string, unknown>;
          /** v46: written only where no row has the record's key (`ON CONFLICT ... DO NOTHING`). */
          insertOnly?: boolean;
      }
    | { kind: 'targeted'; steps: TargetedStep[] };

const upsert = (map: string): MutatorSpec => ({ kind: 'upsert', map });
const insertIfAbsent = (map: string): MutatorSpec => ({ kind: 'upsert', map, insertOnly: true });
// upsertGuarded is NOT defined here: PR 2 has no caller, and @typescript-eslint/no-unused-vars is
// 'error' (packages/api/eslint.config.js:43). v46 brings it with its one caller.
```

`insertIfAbsent` is likewise defined only in **C3**, with its first callers (`createUser` and
the other creates of §3.1), for the same lint rule (critique round 3, gap 2). It is **not**
exported to give C2's tests a caller: v46's line is a non-exported `const` (`v46
pgDescriptors.ts:593`, unchanged at `e6530e54b4`), and §2.6 counts on the two lines being
identical.

-   `WriteBehindQueue.enqueueUpsert(mapName, record, guard?: Record<string, unknown>, insertOnly = false)`:
    v46's signature and its `...(guard ? { guard } : {})` spread; PR 1's fence key stays in the
    body (`writeBehindQueue.ts:154-159`). `WriteOp`'s upsert variant gains v46's `guard?` and
    `insertOnly?` fields next to PR 1's `fence`.
-   `buildUpsertSql(plan, columns, guardColumns: string[] = [], insertOnly = false)`
    (`pgWriter.ts:170-180` today): v46's body, **plus `RETURNING <conflict columns>`** at the end,
    and the guard comparison written through `guardCondition(column, `${table}.${c}`, `$n`)`
    (type-aware: millisecond timestamps, `jsonb`, `IS NOT DISTINCT FROM`, `pgWriter.ts:349-358`)
    instead of v46's plain `=` (`v46 pgWriter.ts:159`). For v46's values (`status = 'pending'`, a
    room id: text, never null) the two forms are identical; PR 1 showed plain `=` matching 1 row in
    2,000 against a `DEFAULT NOW()` column.
-   `upsertRecord(client, plan, record, guard?, insertOnly = false): Promise<boolean>`
    (`pgWriter.ts:183-196` today): v46's body and **both of its throws kept verbatim** (`insert-only
write on <table> carries a guard`; `upsert guard on <table> names a field with no column or
value`, `v46 pgWriter.ts:186-199`; its test asserts those texts,
    `v46 test/deadman-release-notices-postgres.integration.test.ts:811-821`), returning
    `res.rows.length > 0`. A `Promise<boolean>` is a superset for v46's callers, which await and
    ignore it.
-   `installWriteThrough`'s upsert wrapper (`store.ts:8516-8522` today: `const result =
original.apply(this, args); if (this.queue && result && typeof result === 'object')
this.queue.enqueueUpsert(spec.map, result)`) becomes:

```ts
self[method] = (...args: unknown[]): unknown => {
    const capture = this.queue ? captureWrites(this.mapByName(spec.map)) : null; // G1
    let result: unknown;
    try {
        result = original.apply(this, args);
    } finally {
        capture?.stop();
    }
    if (this.queue && capture && capture.prior.size > 0 && result && typeof result === 'object') {
        this.queue.enqueueUpsert(
            spec.map,
            result as Record<string, unknown>,
            spec.guardOf?.(args),
            spec.insertOnly
        );
    }
    return result;
};
```

**G1 — a call that wrote no key queues nothing.** `capture.prior.size === 0` means the method
read the map and returned a record without writing (U1 already forbids in-place assignment into a
record, `store-spec-coverage.integration.test.ts:187`, so a write the capture cannot see does not
exist). This closes O3's "a call that changes nothing still rewrites its row, whole" for the
upserts whose method **returns without a `set`** — the five idempotent creates among O3's eleven
and every other early-return — across **all 220 upserts**, with no spec change. It does **not**
silence an upsert whose method re-`set`s an equal record: `captureWrites` notes every `set`
regardless of value (`store.ts:8445-8448`), so `PUT /streams/:id/moderation` with an unchanged
body (`modules/streaming.ts:1068-1073` → `upsertStreamModeration`), `upsertStream`
(`:2666-2674`) and `upsertCanopySubscription` still write their whole row; the honest sentence for
the headers is therefore "a call that **leaves its row untouched** writes nothing" (§7, critique
round 2, gap 6b). The record written is still the method's returned record, as today. A method
that calls another specced method shares one shadow between the two captures
(`store.ts:8421-8422`): `publishReleaseIdentity` sees its supersedes in its own capture
(`prior.size > 0`) and enqueues its returned record, the new row, exactly as today; the supersedes
are the inner wrapper's own ops (§2.5).

**G2 — a refused upsert re-reads and is not announced.** In `run()`'s upsert branch
(`writeBehindQueue.ts:229-268`): `const applied = await upsertRecord(client, plan, op.record,
op.guard, op.insertOnly)`. When `applied` is false (`DO NOTHING` hit an existing row; a guard was
false), the `'u'` publish at `245-250` is skipped and, **after the fence is lowered** (as the
targeted branch orders it, `223-225`), the record's key (`kvOf(plan, op.record)` → `keyOfTuple`,
`pgWriter.ts:153-169`) is handed to `onRereadKeys` → `refreshKeys`: the writer's mirror takes
Postgres's row (for `addCircleEdge` on a stale process: the existing edge's `id` and
`created_at`) or drops the key. This is the record's decision-4 overlap **(c)** ("a guarded or
insert-only upsert Postgres refuses leaves the writer's own mirror ahead of Postgres, and nothing
re-reads it"), closed for both branches whichever lands second.

SQL: `INSERT INTO t (cols) VALUES (…) ON CONFLICT (keys) DO NOTHING RETURNING keys`
(insert-only); `… DO UPDATE SET c = EXCLUDED.c, … [WHERE <guardCondition …>] RETURNING keys`
(guarded; v46's two specs only).

### 2.3 `STICKY_COLUMNS` (declared once, `pgDescriptors.ts`, after `USER_AUTH_ARTIFACTS`), checked at boot

**Departure** from attack-first's `COALESCE` table rule applied in every builder: a sticky column
is written as `c IS NULL` in the `patch`'s `WHERE`, so a second writer is **refused, counted and
re-read**, not silently merged. This is PR 1's own shape for the same idea (`consume`:
`consumed_at IS NULL`; `revokeRefreshTokensWhere`: `revoked_at IS NULL`;
`markEmailVerificationTokenSent`: `sent_at IS NULL`; `pgDescriptors.ts:622-656, 784-794`), and it
keeps every column of the kept row from one writer (a `COALESCE` form lets a later `updated_at`
land next to the first `revoked_at`). Where a write must land even though another process set the
sticky column first — account deletion's `eraseReleaseIdentity`, whose blanks must not be refused
because a stale copy lacked `superseded_at` — the spec names the column in `keepStored` and that
one column is written `COALESCE(c, $n)`. Nothing is added to `buildUpsertSql`: after PR 2 no plain
`upsert` remains on a sticky table, and U8 fails the build if one is added.

### 2.4 Two `upsertEach` options (PR 1's region)

-   `onConflictWhere?: string` — a literal appended as `DO UPDATE SET … WHERE <literal>`. Used
    once, for `revoked_sessions`: `revoked_sessions.revoked_at <= EXCLUDED.revoked_at`. A row-level
    monotonic rule, so the later cutoff wins and `reason`, `expires_at`, `user_id` come from the
    same write (the PR 1 design's `pgsem.log` S2 showed per-column `GREATEST` mixing an older
    `reason` with a newer time). Both times are API-stamped ISO millisecond strings
    (`store.ts:1157`), so `<=` is exact; an equal time lets the later-landing write through, which
    is harmless. **Departure** from attack-first's `upsertWhere` table rule in both builders: no
    other method writes `revoked_sessions` by upsert (`pruneExpiredRevokedSessions` is targeted;
    `revokeUserTokensBefore`, `1195-1202`, has no spec of its own and writes through the wrapped
    `revokeSession`, which U1 accepts as "a specced callee's writes are persisted by that callee's
    own wrapper", `store-spec-coverage.integration.test.ts:170-176`), so the step option is enough
    and touches no v46 hunk.
-   `conflictTarget?: string` — a literal replacing `(<conflict columns>)` after `ON CONFLICT`.
    Used for aid posts mirrored by origin (§6) and, through `patch`'s insert branch, for external
    replies (§3.5). `compileStep` runs `literal()` on both (no `;`, non-empty); the boot `PREPARE`
    validates the column names and, for a partial-index arbiter, that an index backs it.

`buildTargetedUpsertSql(plan, columns, onConflictSet, { conflictTarget, onConflictWhere, insertOnly })`.
`revokeSession`'s statement:

```sql
INSERT INTO revoked_sessions (jti, user_id, revoked_at, expires_at, reason) VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (jti) DO UPDATE SET user_id = EXCLUDED.user_id, revoked_at = EXCLUDED.revoked_at, expires_at = EXCLUDED.expires_at, reason = EXCLUDED.reason
WHERE revoked_sessions.revoked_at <= EXCLUDED.revoked_at
RETURNING jti
```

Refused (an older cutoff landing after a newer one): 0 rows → the key is in `touched`, not
`returned` → re-read; the loser's mirror takes the newer cutoff; nothing announced for it. Bonus:
a sign-out's notification moves inside its transaction (`'k'`), so a committed sign-out can no
longer go unannounced; O4's "`revokeSession` is an upsert" case closes. Cost: a `NOTIFY` failure
now fails the sign-out write (O14 class; the payload is one short jti).

### 2.5 Rule for a targeted spec over a method that calls another specced method (missed by all three)

`installWriteThrough` sets the wrappers as instance properties (`store.ts:8513, 8516`), so a
method that calls `this.other(...)` reaches the **wrapped** `other`, which queues its own op, and
`captureWrites` shares one shadow between nested captures (`8421-8422`), so the outer call's
capture also records the inner call's keys. A `patch` bound from the outer `ctx.changed(map)`
would bind the inner call's keys a second time: the inner lands, the outer is refused and counted
on every call. In the tree the one such pair on a converted map is `publishReleaseIdentity` →
`this.supersedeReleaseIdentity` (`2598-2600`). PR 2's rule:

-   **A `targeted` spec must not sit on a method that calls another specced method writing one of
    the outer spec's maps.** Pinned by **U9** (§8), a static check on U1's method scan
    (`info.calls`, `store-spec-coverage.integration.test.ts:165-182`).
-   `publishReleaseIdentity` is therefore `insertIfAbsent('releaseIdentities')` (upsert kind): the
    wrapper enqueues only the **returned record**, the new row, as today; the supersedes are
    `supersedeReleaseIdentity`'s own `patch` ops, queued first (FIFO), which is the order the store
    method's comment asks for (`2588-2592`). No frame bookkeeping is needed.
-   `revokeUserTokensBefore` → `this.revokeSession` is the same shape with no spec on the outer
    method, so nothing binds twice (§2.4).

`InMemoryDb.accountExists(id): Promise<boolean>` → `Promise.resolve(this.users.has(id))`
(memory and file stores: mirror only). `PostgresBackedDb` overrides it (**option B**, at the end of
the class, outside every v46 hunk), and the miss-path read **runs on the FIFO apply chain**:

```ts
override async accountExists(id: string): Promise<boolean> {
    if (this.users.has(id)) return true;
    const plan = this.plans.get('users');
    if (!plan || !this.pool) return false;
    try {
        // One keyed SELECT by primary key, queued on the apply chain behind every refresh already
        // queued (a peer's 'k' for this key among them) and awaited, bounded; a timeout or an error
        // (a non-uuid sub) counts as absent.
        await this.awaitWithin(this.refreshOnChain(plan, [[id]]), ACCOUNT_CHECK_TIMEOUT_MS /* 250 */, 'auth_account_check');
    } catch (err) {
        log.warn('auth_account_check_failed', { error: err instanceof Error ? err.message : String(err) });
        return false;
    }
    return this.users.has(id);
}

/**
 * Queue one keyed refresh on the apply chain and settle when it has run. A failure rejects the
 * caller's promise and is NOT rethrown into the chain: onApplyChain's own catch (store.ts:8776-8787)
 * logs pg_store_peer_refresh_failed for anything that throws, and the caller already logs
 * auth_account_check_failed, so a miss of a non-uuid subject must not log twice (critique round 2, gap 8b).
 */
private refreshOnChain(plan: TablePlan, kvs: unknown[][]): Promise<void> {
    return new Promise<void>((resolve, reject) => {
        this.onApplyChain('auth', async () => {
            try { await this.refreshKeys(plan, kvs); resolve(); } catch (err) { reject(err); }
        }, plan.descriptor.mapName);
    });
}

/** Race a promise against a timer that is cleared and unref'd; the promise itself is never cancelled. */
private awaitWithin<T>(p: Promise<T>, ms: number, what: string): Promise<T> { /* backgroundLeader.ts:149-156's shape */ }
```

**Why the chain (G2 of the first critique).** PR 1 built `onApplyChain` (`8776-8787`) so refreshes
of one key never reorder (O11): a peer's `'k'` (`applyPeerChange`, `8948-8966`), the queue's own
re-reads (`8756-8764`), reloads and rehydrates all run through `applyTail`. A read sent
_outside_ the chain can resurrect a deleted row: B's `SELECT` snapshot predates A's `deleteUser`
`COMMIT`; A's `'k'` arrives and B's chained refresh runs (`refreshKeys`: row absent → `map.delete`,
a no-op); then the direct read's reply applies, and because `map.get(k)` and `seen.get(k)` are both
`undefined` the "changed while in flight" test at `8860` does not fire and the row is **set**
(`8865`). B then holds a deleted account although it heard the deletion, nothing re-reads the
key again (the row is gone, no later change), and the token is accepted on B until restart or
expiry. On the chain the order is fixed: the read runs first (it was queued first), sets the row;
the `'k'` refresh runs after it and removes it. The request whose read overlapped the deletion is
accepted **once** (the account existed at the `SELECT`'s snapshot); the next is refused. Pinned by
**M5** (§8), which holds the read's reply with the harness's `hold` while the deletion's `'k'`
lands. `refreshKeys` runs its `SELECT` through `withClient` as a plain statement (`8847`), not in
a transaction, so holding it is allowed on PGlite (§8's harness rule).

**What the awaited read sees.** `refreshKeys` (`8836-8871`) is PR 1's fenced path: a `SELECT x.*
FROM users … WHERE id = ANY($1::uuid[])` (`selectByKeysSql`, `pgWriter.ts:538`), a found row set
into the mirror, a key with no row left absent. **A key this process has a queued write for is
skipped and marked dirty** (`8856-8858`; `isFenced`, `writeBehindQueue.ts:127`): the case that
matters here is a **queued `deleteUser`**, whose targeted op fences `users:<id>` from enqueue until
it lands (`enqueueTargeted`, `writeBehindQueue.ts:147-152`) while the mirror already lacks the
row — so on the deleting process, between the route's `deleteUser` and its `DELETE` committing,
`accountExists` misses the mirror, the chained read skips the fenced key, and the request is
refused. That is the right outcome and the reason the deleting process refuses the account's
token from the moment the route ran, not from the moment Postgres caught up. A non-uuid `sub`
(`demo-user` after a reload; a forged subject) makes Postgres reject the cast: rejected to the
caller, caught, logged once, absent. A timed-out read still completes later, **in chain order**,
and sets the mirror: harmless by construction now, and the next request with that subject passes
without a read.

**Helpers are new.** `withTimeout` in `src/integrations/http.ts:14-31` is a _fetch_ wrapper
(`AbortController` on a request) and is not reusable for a promise; the promise-bound pattern
exists only inline (`services/backgroundLeader.ts:149-156`: a `setTimeout` reject raced with the
query, timer cleared). PR 2 adds `awaitWithin` and `refreshOnChain` as private methods of
`PostgresBackedDb` (C6's file list, §9), not in `integrations/`.

**No negative cache in PR 2.** Attack-first's 5 s cache on a miss would turn the window below
into a 5 s refusal of a brand-new account on another replica. A flood of a deleted account's
token costs one indexed primary-key `SELECT` per request on that process (each queued on the chain
and awaited), bounded by the global rate limit (`index.ts:174`).

**A busy chain.** The 250 ms bound covers everything queued ahead of the read: normally a few
single-key `SELECT`s (each about a millisecond), but behind a whole-table reload (`'r'` from a
previous-release process, or a rehydrate after a listener reconnect, `8769-8771`) it can expire.
Then the request is refused once (fail-closed, `auth_account_check_failed` with the timeout
message), the read still runs when its turn comes and sets the mirror, and the next request
passes. Rare (both reloads are rare), bounded, and honest; said in the record and
`KNOWN_LIMITATIONS.md` (§7).

**Why not the mirror alone (the operator's literal words, option A).** A mirror-only check
wrongly refuses a legitimate new account on any process that has not heard of its `createUser`:
(i) in the notification lag after `/register`, the exchange's auto-provision or the first OIDC
login (p99 16 ms, max 32 ms on loopback PG16); (ii) **for good**, on a process that missed the
`'u'` (the boot gap: 229 of 425 sign-outs missed in the reviewer's run; a failed after-commit
publish; a half-open listener): today such a process fails only `/token/refresh` and
`/password/change` for that account; option A makes it fail **every** request until it restarts
— a new permanent failure mode. Option B turns (i) and (ii) into one `SELECT` on the first request.

**Response code.** `session_revoked` is reused. The client handles no code by name
(`apps/blackout-client/src/client/blackoutApiSession.ts`; the one mention of `session_revoked` in
the client is a comment in `invitationsClient.ts:178`): on any 401 it clears the API token and
re-exchanges its Matrix session. A valid signature already proved the account existed, so the code
leaks nothing new. Q7 if a distinct code is wanted.

The session is issued as soon as the **mirror** has the row; the `INSERT` reaches Postgres "just

### 4.4 Who it still does not refuse, and what the record must say

-   **A process whose mirror still holds the deleted account** (it missed `deleteUser`'s `'k'`: the
    boot gap or a half-open listener, since that `'k'` is inside the transaction) keeps accepting
    the token until it hears or restarts — the same class as a missed sign-out (O4). On such a
    process `/token/refresh` also finds both the account and the refresh token in its mirror and can
    mint **one fresh 24 h access token per refresh token it still holds** for the account; the
    rotation `patch` then misses in Postgres (`refresh_tokens` rows are cascaded) and the successor
    `INSERT` fails its foreign key, so it is bounded, but O6's "until it expires" understates it;
    the record says this (judges' item 3). With the read on the chain (§4.2) this is the **only**
    residual for the account's tokens in general; for the **one token that confirmed the deletion**
    the moved denylist write (§4.5) narrows it further on every mirror whose refresh of that
    revocation ran before the cascade.
-   **O5 interplay** (judges' item 2 of "missed by all"): `deleteUser` fails in Postgres for an
    account with messages, votes or tips (non-cascading foreign keys: `messages.user_id UUID
REFERENCES users(id)`, `001:37`, and others); the deleting process's mirror has dropped the
    account; the holder's next request on that process misses the mirror, the miss-path `SELECT`
    finds the row and **puts the account back into that mirror**: the account the user was told was
    deleted works again on the very process that deleted it. Correct state (the account does exist),
    surprising behaviour; the record's O5 bullet says so. The confirming token is **still refused**
    in this case, on every process that heard of it, because its revocation landed before the failed
    delete and the row stays (§4.5) — as today, and unlike the previous version of this design, which
    removed the write and would have let that token live again (critique round 2, gap 2; "every
    process" narrowed by round 3's gap 5).
-   **The client's 401 path** (judges' item 2): it re-exchanges the Matrix session. Blackout account
    deletion does **not** deactivate the Matrix account (`services/accountLifecycle.ts:293-335` and
    `routes/auth.ts` call no `deactivate`; the only Matrix deactivation in the API is for burner

-   **The demo seed** after a `users` reload or rehydrate is refused (never in Postgres). Pre-existing
    oddity; one sentence in the record.
-   **A subject not in the mirror while the chain is behind a whole-table reload**: refused once

### 4.5 The deletion's denylist write moves before the delete (S8; critique round 2, gap 2)

Today `/account/delete/confirm` writes `revokeSession({ jti, userId, expiresAt, reason:
'account_deleted' })` **after** `confirmAccountDeletion` (`routes/auth.ts:1090-1101`), which has
already queued `deleteUser`. In Postgres mode that row can never land
(`revoked_sessions.user_id REFERENCES users ON DELETE CASCADE`, `007:49`): the write is queued
behind the `DELETE`, fails its foreign key, is retried, fails, and counts in
`db_write_behind_failures_total` on **every** deletion — the one steady source of that counter.
The previous version of this design removed the write as "redundant with the existence check in
every mode". That is false in the one case where the deletion **rolls back** (O5: `deleteUser`
fails in Postgres for an account with non-cascading children, the `users` row stays): today the
post-delete upsert then succeeds (the FK holds) and the confirming jti is refused on every process
that heard of it; with the write removed, the deleting process's mirror lacks the account, the
miss-path read puts it back (§4.4) and the token is accepted there, and every other process never
dropped the account and accepts it too — a token the user was told died, live again. Removal also forgoes a free narrowing
of O6's residual. So PR 2 **keeps the write and moves it**:

-   `confirmAccountDeletion(presentedToken, authedUserId, session?: { jti: string; exp: number })`
    (`services/accountLifecycle.ts:293`). After the four token checks pass (`:298-302`) and **before**
    `consumeAccountDeletionToken` (`:305`), it writes
    `db.revokeSession({ jti: session.jti, userId: record.userId, expiresAt: new Date(session.exp * 1000).toISOString(), reason: 'account_deleted' })`
    when a session is given. Placed above the consume so the insertion stays clear of v46's hunk as it
    was at `e9556d76dd`, which began after the dead-man comment (an insertion after base `:313`;
    §2.6 overlap (h)); at `e6530e54b4` that no longer holds (the merge note below).

**Why it lands, sticks and is announced.** The write-behind queue is one FIFO chain for every
kind (`schedule`, `writeBehindQueue.ts:182-187`: `this.tail = this.tail.then(() => this.run(op))`),
so the revocation runs before the consume, the five erasures, the purge and the `DELETE`
(`:305-333`), while the `users` row exists: the FK holds. `revokeSession` is a targeted
`upsertEach` after §2.4, so its `'k'` is published **inside its own transaction** and the row is
`RETURNING`-checked. The `DELETE` then cascades the row away in Postgres. In the mirrors:

-   the **deleting process** keeps the revocation: `deleteUser` is `this.users.delete(id)` only
    (`671-673`) and `revokedSessions` is in `USER_CASCADE_LEFT_IN_MIRRORS` (`pgDescriptors.ts:702-704`),
    so its own cascade never removes it (D1). The confirming token is refused there from the route's
    return, whatever the existence check does;
-   a **peer whose refresh of `revokedSessions:<jti>` runs before the cascade commits** sets the row
    and, by D1, keeps it until restart: the token is refused there **even if that peer later misses
    the deletion's `'k'`** (the §4.4 residual) — the narrowing the critique named;
-   a **peer whose refresh runs after the cascade** finds no row (`refreshKeys`: absent →
    `map.delete`, a no-op on a key it never held) and never holds the revocation. The `DELETE` is a
    handful of queue ops behind the revocation (each a round trip of about a millisecond on
    loopback), and a peer's refresh lands at p99 16 ms, so which case a given peer is in is a race of
    milliseconds; the record states both outcomes rather than claiming "every mirror";
-   on **O5's rollback** the `users` row and the revocation row both stay in Postgres: every peer's
    refresh of the revocation finds it, and the token is refused on every process that heard of it,
    as today (a process in the boot gap or with a half-open listener never re-reads the
    revocation's `'k'`, O4; critique round 3, gap 5).

## 7. D1's decision text, the record's new section, `KNOWN_LIMITATIONS.md` and the comments

### 7.1 Decision text (goes under "Where the build departs from the design", numbered on from D10)

> **D11 — D1 is confirmed (operator, 2026-10-31).** When an account is deleted, Postgres removes
> its `revoked_sessions` rows by the foreign-key cascade alone: `deleteUser` does not delete them
> explicitly and no mirror is told, so every running process keeps refusing the account's revoked
> access tokens and keeps its logout-everywhere cutoff until that process restarts. This is the
> behaviour wanted. Telling the mirrors would make every process accept those tokens at once, for
> the rest of the tokens' lifetime (up to 24 hours). Since PR 2, a process that has heard of the
> deletion refuses the account's tokens anyway, because the auth middleware refuses a token whose
> account no longer exists; the kept rows matter on a process that has not heard of it yet, where
> they still refuse the tokens the account had revoked — the deletion's own confirming token among
> them, which is now revoked before the account is deleted so that revocation lands and is heard.
> Nothing reads a revocation as proof that an account exists. `USER_CASCADE_LEFT_IN_MIRRORS` holds
> this one exception, U7 checks the two lists against the foreign-key catalogue, and X17 checks
> that a peer still refuses the token after the deletion. "For the operator" item 8's question is
> answered.

   the full `test:integration` run at C2 (§9). A method that writes a map other than its spec's
   map is already a U1 failure.
3. **A `patch`'s run-time SQL is per call.** Only the all-columns check statements (both branches:
   `checkSql` and `insertCheckSql`, §2.1) are `PREPARE`d; a type mismatch surfaces at run time as a failed write, counted and logged, as a
   failed upsert is today.
4. **The password CAS, narrowed.** It refuses the second of two legitimate **changes** racing on
   two processes within the notification window, after its 200 (O24, Q5); a change on a process
   that missed the last change for good is refused by the route before any write (read staleness,
   pre-existing); **a reset is never refused** (`resetUserPassword`, no CAS, D23). The alternative
   to the CAS lets a stale replica revert a password change for an attacker holding the old
   password.
5. **Benign conflict counts.** `db_targeted_write_conflicts_total` gains a stale re-revoke of a
   bot credential, a redelivered external reply and a stale insert-only no-op (the latter through
   G2 is not counted; only patch refusals are). No alert reads it today (O21). The `{map, method}`
   labels already separate a refused stale write from a bounty gate miss.
6. **O14 reaches `revokeSession`**: a `NOTIFY` failure fails the sign-out write (retried, counted).
   It does not reach the creates (D15). The deletion's pre-delete revocation is a `revokeSession`,
   so a `NOTIFY` failure there fails that one write too (counted; the deletion itself proceeds).
7. **`'replace'` and `'add'` are reached only by a process that never saw the row.** Their safety
   rests on the callers read in §3 (every field fresh from the request; counters from a zero
   base). A future caller that builds a linked-account record from the mirror would reopen the
   whole-row hazard for that one table: the spec's comment says so.
8. **Option B's awaited read** in the middleware on a miss; fail-closed on a Postgres outage for
   subjects not in the mirror (Q1); a once-refusal behind a whole-table reload (O23); window (iii)
   (Q3). The read sits on the apply chain: a long reload ahead of it is what the bound is for.
9. **The 44-file fixture diff**: a subject that is load-bearing for a 403 assertion must seed a
   different user; reviewable per file.
10. **Partial-index `ON CONFLICT`** for aid posts and external replies: inference semantics checked
    by `PREPARE`, X23b and X34 on both backends at build time.
11. **The moved denylist write is a race against the cascade for the peers.** It is strictly
    better than today (which never lands it) and than removal (which loses the O5 case), but the
    record must not say "every mirror": a peer whose refresh runs after the cascade never holds it
    (§4.5). X37(b) pins the before-cascade case; the after-cascade case is the §4.4 residual and is
    stated, not tested as a guarantee.
