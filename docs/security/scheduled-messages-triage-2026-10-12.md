# Scheduled messages and bot posting — triage of the 2026-10-12 live run

Run date: 2026-10-12, against `develop` at `1555912`. This record is written
with the fixes that close most of its rows, in the same change set.

The rule from the earlier triage passes applies: every finding gets a fix or a
written explanation, and nothing is baselined silently.

## What was run

The API was started in memory mode with `MATRIX_HOMESERVER` and
`MATRIX_BOT_TOKEN` pointed at a stand-in homeserver that answered the bot's
`whoami`, the Synapse admin user and room endpoints and every `/send/` call with
success, and recorded each request as it arrived. The mailer was pointed at a
stand-in SMTP server that kept every message, so account-deletion tokens could
be read back. A probe script registered users over HTTP and drove
`/v1/scheduled-messages`, `/v1/messages`, the account export and the
account-deletion flow. The composer was driven in jsdom with a fake encrypted
room. A second pass tried to refute each finding by reading the code and
re-running parts of the probe.

**Observed** below means a request or response was recorded in that run.
**Read** means the claim rests on the code alone. The transcripts are kept with
the investigation notes, outside this repository. What lives in the repository
is a test for each observed behaviour, driving the real Hono app against a stub
homeserver (`packages/api/test/_fixtures/matrixStub.ts`), so CI's
`api-smoke-and-integration` job keeps this record honest.

## Left open, and what each waits on

-   **N3a — scheduling in encrypted rooms.** Refused for now (S2). The options are
    a client-held delayed send (works only while a device is online, and must say
    so), a server-sent pre-encrypted event (appservice impersonation plus Megolm
    key timing), or giving the bot crypto, which would make it a reader of those
    rooms and break TRUST.md's "no bot can read your encrypted messages". Also to
    decide: whether to hide the preset where it can never work, since the bot
    joins canopies rather than dens.
-   **N3b — list, cancel and failures in the app** (S4/E3).
-   **N3c — `formatted_body`** (E2): plain body only, or a server-side sanitiser
    shared with the composer's allowlist.
-   **N3d — a per-user pending cap.** Only the global limiter applies today.
-   **N4 — the Matrix account after deletion** (E4). Deactivate first and keep the
    API account on failure so the user can retry; counsel to confirm the
    privacy-policy wording.
-   **N5 — an "unencrypted" marker in the timeline** (P2).
-   **Legacy channel membership** (a): non-DM channel ids are readable, and
    DM-shaped ones writable, by any signed-in account.
-   **Where delivery runs.** The dispatcher posts only where the background loops
    run against the loaded store. In `deploy/docker/production` the loops run in
    the worker, which did not load the store at `1555912`; scheduled messages were
    stored there and never posted. Fixed in a separate change on 2026-10-23: the
    worker loads the store through the API's own boot before any loop starts
    (`packages/api/src/backgroundWorker.ts`). With it, a message the dispatcher
    reaches more than the backlog tolerance after its time (15 minutes at the
    default cadence) expires unsent: it ends `failed` with `lastError`
    `expired_overdue` and its text cleared, the retention every finished row
    gets (P1). So the first working start posts none of the backlog, and the
    authors are not told (S4/E3). Tests B-1 to B-5 in
    `test/scheduled-messages.integration.test.ts`.

Not in this record: findings from the same investigation about other features
are triaged with their own fixes.

## Still unverified

-   Whether this Synapse fork stores a plaintext `m.room.message` posted into an
    encrypted room. The spec allows it and the fork's module does not refuse it;
    the fork could not be run during the investigation.
-   The admin room-state endpoint on a running fork. The gate relies on it; the
    invite flow already depends on the same admin endpoints, and the fork serves
    it (`synapse/rest/admin/rooms.py`).
-   Whether the bot is really joined to encrypted dispute and delivery rooms in
    live deployments. The code creates them with the bot as creator.
